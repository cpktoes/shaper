<objective>
The founder noticed that changing a wing's corner radius moved their quad's rear fins, and ruled (2026-10-15): "I
think the fin placement should be linked to the unrounded outline, so that the rounding has no affect on fin
placement. It's the wing position that does." In a shaper's words: the rounded wing corners stay exactly as they are
on every drawing and print, but every fin number is now worked out as if the wing's corners were sharp — so turning
the corner-radius slider never moves a fin, while sliding the wing, or changing its depth or run, still does.

Purpose: the brief's locked ruling (D1–D3) plus the founder's follow-up ruling on the FINS drawing (D4). The
calculators are the product (CLAUDE.md Rule 1), so the proof is a radius sweep over every fin setup in pure tests, and
one browser test on FINS that fails on today's code.

Output: one pure helper in `lib/geometry/wings.ts`, two call sites (the wing lock and the design store), FINS' tail
drawing split from the fin maths' tail, comments, unit tests, one desktop browser test, two corrected notes.

  step. "Every fin calculation" is three reads: the 12" tail width the fins take (`deriveEffectiveFins`), the real tail

  fin placement inside `resolveWingStations` (`placeFins`), which must read the same sharp outline as the screen or the
  lock and the screen would disagree.

  outline for the maths. FINS' code comment says plainly that a fin's in-from-the-rail number is measured to the sharp
  step, not to the drawn rounded rail.
