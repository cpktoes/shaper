<objective>
Make the 12px content inset a property of `TabbedPanel` itself rather than something each
screen does, does differently, or forgets. Today Volume passes it as `panelClassName`,
Template gets the same look from its own child div's padding, and Rails and Fins have
nothing — their plots and tables sit flush against the content card's border.

Purpose: the founder asked for the indent Volume has on every other tab. But the underlying
problem is that one treatment is being arrived at three different ways, which is exactly the
drift `TabbedPanel` was extracted (quick task 260825-pkq) to stop — its own docstring says
so. Setting the default in one place both answers the request and removes the two redundant
copies, so Rails and Fins get it for free and so does the next screen anyone adds.

Output: `TabbedPanel`'s inner content card carries the inset by default; the copies at the
Volume and Template call sites are removed; the two sub-inset nudges on the Rails and Fins
viewers go with them.
</objective>

  <name>Task 1: Default the inset in TabbedPanel and drop the two copies that duplicated it</name>
  <files>components/viewer/tabbed-panel.tsx, components/volume/volume-estimator.tsx, components/outline/outline-editor.tsx</files>
  <action>
These three edits land together — separately they leave Template with a doubled inset.

**components/viewer/tabbed-panel.tsx** — give the inner content card (the one carrying
`rounded-lg border border-surf-line-faint bg-surf-panel`, around line 98) a default padding
of `p-3`: the same 12px the outer panel uses and the same value Volume passes today.
Compose that class list with `cn` from `@/lib/utils` instead of the current template
literal, so `panelClassName` is merged rather than concatenated. With a plain string, a
caller passing its own padding would win or lose depending on Tailwind's stylesheet order,
which is not something a call site can reason about; `cn` wraps tailwind-merge, so the
caller's padding deterministically replaces the default. `cn` is already the app's
convention — every `components/ui/*` file imports it. Leave the card's surface, border
token, radius and flex classes exactly as they are.

Then update the two comments that are now out of date. The `panelClassName` doc comment
currently reads "layout only; surface and edges are fixed here" — it should also record that
the card supplies a default inset and that a caller passing its own padding overrides it.
And the inner card's block comment should gain a sentence saying the inset lives here on
purpose, so that every screen and every tab gets one treatment from one place. That sentence
is the thing this task exists to protect.

**components/volume/volume-estimator.tsx** (line 33) — `panelClassName` should now carry
only the scrolling behaviour, `overflow-y-auto`. The padding it was passing is the default;
passing it again would be the duplicate this task is removing. Nothing else on this screen
changes, and it should look identical afterwards.

**components/outline/outline-editor.tsx** (around line 156) — the viewer's content div
should end up with the class list `relative flex min-h-0 flex-1 items-stretch justify-center
gap-6`, losing only its own padding. Keep the div and keep `relative`: it is load-bearing,
it is the positioning context for the rotate button per D-06, and the comment above it says
so. Its content box works out identical either way, so the board does not change size.

One consequence to handle rather than leave. The rotate button is absolutely positioned
against that div, and an absolute child is offset from its containing block's *padding* box.
With the inset now on the card instead of the div, the button's current offsets would push
it 12px further down and further in. Rebase them to zero — `absolute top-0 right-0 z-10` —
so the button lands on the content area's corner, which is exactly where it renders today,
12px from the card's border. Leave the rest of that button's class list alone: its border,
its opaque fill, its hover and focus rings all stay. Add a short comment on the offsets
explaining they are zero because the card now supplies the inset, so a later reader does not
"correct" them back.
