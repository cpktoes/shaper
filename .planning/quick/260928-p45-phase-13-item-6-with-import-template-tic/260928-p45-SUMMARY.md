# Phase 13 Item 6: Fins Follow the Real Drawn Tail — Summary

**With Import Template ticked, FINS now measures every rail-referenced fin off the outline actually drawn on TEMPLATE, using the prototype's own imported-template branch ported into `lib/geometry/fins.ts`; unticked, nothing changes.**

## What changes on screen

With the Import Template box ticked (the default, and the way most shapers will use the app),
each fin that is measured "in from the rail" — the thruster/quad front pair, the twins, the 2+1
side bites, and the quad's rear pair on the Basic Off-Rail model — now reads its position off the
board's ACTUAL drawn tail, not off a generic curve fitted only to the tail width and shape. That
shows up in three places that all agree with each other because they all read the same numbers:
the FINS screen's own drawing, the fin marks drawn on TEMPLATE's outline, and the Summary order
form's bottom view.

Measured moves, comparing the real rail to the old generic curve, at each board's own fin
stations:

- **Fish:** the twin fins sit about **0.17 in (roughly 3/16 in) further out** — the Fish's tail is
  a bit fuller there than the generic curve assumed.
- **Mid-length:** the rear quad fins sit about **0.19 in further in** — the round tail there is a
  little narrower than the generic curve at that station.
- **Shortboard:** effectively no visible move (about 0.001 in).
- **Longboard:** no move at all — it's a single fin on the centreline, which was never measured
  off the rail.
- **The app's own default board** (a 6'0" squash-tail thruster, before any preset is picked): about
  **0.012 in**, well under what a shaper could see or measure.

The tail-end extension line drawn on FINS also gets a little more accurate: on the default board
it now stops at the real tail corner (2.00 in half-width) instead of the generic curve's slightly
wider 2.32 in — about 4.5 drawing units shorter, no text change.

## Why no written or printed number changes

Every number on the DATA tab and every printed measurement — off-tail, off-rail distance, toe-in,
base length, full spread — is a length or a distance-from-a-fixed-point formula. None of those
formulas reads the tail's shape at all; only the LATERAL POSITION of a rail-referenced fin (how
far from centre it's drawn) depends on the width of the rail at that fin's own station, and that's
exactly the number this change corrects. A dedicated test (`fins-imported.test.ts`, "no written
fin number moves with the real tail") proves every case's `sections` — the numbers a shaper reads
or prints — come out byte-for-byte identical with and without the real tail.

## Unticked stays exactly as it was

With Import Template unticked, FINS is still the standalone calculator on the generic tail curve —
useful when a shaper wants fin numbers without having drawn a board first. `computeFinPlacement`
called with no second argument (or with `null`) is proved deep-equal, fixture by fixture, to what
it always returned; `npm run golden` regenerates the three untouched fixtures
(`prototype-outline-golden.json`, `prototype-rails-golden.json`, `prototype-volume-golden.json`)
and the original `prototype-fins-golden.json` byte-for-byte identical.

## Saved boards

Nothing stored on a board changes — fin placement is derived from the board's own outline and fin
spec every time it's drawn, never saved as its own field. A board saved before this change, once
reopened with the box ticked, simply draws its fins off its own real rail from that point on; a
board saved with the box unticked keeps behaving exactly as before.

## How this was checked

- **`npm test`:** 3,086 tests passed before this task (unchanged suites); 234 new tests were added
  in `lib/geometry/fins-imported.test.ts` (golden parity on 32 boards, tail-adapter parity on 9
  outlines, probe parity, the unticked-unchanged guard, and the no-written-number-moves guard). The
  full suite now runs **3,320 passed, 2 skipped, 0 failed**.
- **Fixture byte-identity:** `npm run golden` was run twice; the fallback fixture and the three
  unrelated fixtures came back byte-for-byte identical both times, and the new
  `prototype-fins-imported-golden.json` (9 outlines, 32 cases) came back byte-for-byte identical on
  its second run too.
- **`npm run lint -- --max-warnings 0`** and **`npx tsc --noEmit`** both exit clean.
- Every expected number for the real-tail path came from executing the prototype's own
  `effectiveHalfWidthAt`, `outlineOffTailAtHalfWidth`, `syncFromTemplate` and `importedOutlinePath`
  (extended `scripts/extract-prototype-fins-golden.mjs`) on the app's own `buildOutline` output for
  the four board presets and each of the five tail shapes — never a hand-typed number.

## The tsx watch item

`npm run golden` (and `npm run golden:fins`) now run the fins generator through `tsx` instead of
plain `node`, because that script imports the app's own TypeScript geometry (`BOARD_PRESETS`,
`DEFAULT_BOARD_SPEC`, `TAIL_PRESETS`, `buildOutline`, `mmToInches`) to build the real outlines the
prototype is fed. `tsx` was already present in `node_modules` — pulled in transitively by
`drizzle-kit` and `vite` — and is now also declared directly as a developer tool
(`devDependencies`, pinned to the version already installed, `4.23.12`), the same posture
`scripts/extract-phase11-foil-golden.ts` already has. Nothing is bundled into the site; this only
affects a developer running `npm run golden` locally. **Watch item:** if a future dependency bump
ever drops `drizzle-kit` or `vite`'s own indirect dependency on `tsx`, this direct devDependency is
what keeps `npm run golden` working — it no longer relies on the transitive copy alone.
