<objective>
A saved board can be locked and unlocked, and a locked board cannot be changed, saved or deleted
by accident. This is the first of two plans: it delivers everything that PROTECTS the board, and
the founder looks at it in the browser before Plan 02 greys out every control on every screen.

What the shaper sees after this plan: on the Board Rack, ⋯ → "Lock board" locks a board, its
caption shows a small padlock, the row now reads "Board Locked" (ticked), and Delete is greyed.
Opening that board, the top bar shows "Unlock" where Save was; nothing they touch changes the
board or saves (sliders and fields simply don't take — the greying itself is Plan 02). Pressing
Unlock unlocks it for good: the board can be changed again, Save comes back, and the rack reads
"Lock board" again. Duplicating a locked board gives an unlocked copy.

Purpose: a finished board (maybe already at the blank shop or the glasser) must stay exactly as it
was when a shaper opens it just to look, or to show someone (todo 2026-10-08, founder spec).
Output: the `models.locked` column (development branch migrated), the lock action and refusals,
the rack toggle, padlock and greyed Delete, the open board's lock in the store, Unlock in the top
bar, and browser tests on a computer and both phones via the practice rack.
</objective>

<planner_decisions>
Each is the planner's call where the founder left room; the founder can overrule any of them.
- P1. Where the lock lives: a nullable boolean column `models.locked` (null or false = unlocked),
  not a field inside the board's `snapshot`. A lock is about the saved record, not the design: the
  board's own data is never rewritten by locking it, a copy's snapshot can never carry a lock
  forward, the rack reads it without parsing the design, and the server can refuse a save or a
  delete in the same statement that would have done it (CLAUDE.md Rule 2's spirit — a setting about
  a record never rewrites the design). Nullable with no default, the project's convention for an
  additive column.
- P2. Locking or unlocking does NOT change the board's `updatedAt`: "Last touched" keeps meaning
  when the board itself last changed, and a board in a never-arranged rack does not jump to the
  front because it was locked.
- P3. Only saved boards can be locked. The unsaved board has no ⋯ menu (today's rule), so a board
  kept only in the browser while signed out never meets the lock.
- P4. The menu row is a checkbox item (`menuitemcheckbox`, ticked when locked) placed between
  Duplicate and Delete; it closes the menu when chosen, and its words are the founder's own:
  "Lock board" / "Board Locked".
- P5. The padlock sits right after the name in the caption (the rack's card), in muted ink — a
  lock is information, never the warning colour (sketch findings: the warning colour is never
  informational). The vertical name beside each standing board gets no picture (its words shrink
  to fit the rack's height in two big files); a screen reader hears "locked" there instead. See
  the founder question in the SUMMARY.
- P6. The Unlock button: the shared outline Button at the small size with a padlock icon, the
  label "Unlock", named "Unlock Board" for screen readers (mirroring "Save Board"), 44 dots tall on
  a touch screen. While unlocking it reads "Unlocking…"; if it fails it becomes the same kind of
  clickable warning-ink words the failed Save uses, "Not unlocked", and pressing them tries again.
  No confirmation step (founder: "When unlock is selected, then the board can be edited").
- P7. A save that reaches the server for a board locked elsewhere (another device) is refused
  without writing and answers "locked", and the editor then turns its own lock on — so the lock
  follows the shaper to a second device that already had the board open.
</planner_decisions>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-lsy-01 | Tampering / Elevation | setModelLocked | high | mitigate | auth() first; the update is scoped by id AND clerkUserId; another shaper's id updates nothing and throws; enforced by ownership.test.ts's existing checks over the new action |
| T-lsy-02 | Tampering | deleteModel | high | mitigate | the delete's WHERE excludes a locked row (`is not true`), so a stale page or a crafted call cannot delete a locked board; the menu row is greyed as well |
| T-lsy-03 | Tampering | saveModel (autosave from a stale tab or a second device) | high | mitigate | the update's WHERE excludes a locked row and answers `locked: true` without writing; the store then turns its own lock on (P7) |
| T-lsy-04 | Tampering | setModelLocked input | medium | mitigate | a non-boolean `locked` or empty id is refused with `saved: false` before any database work |
