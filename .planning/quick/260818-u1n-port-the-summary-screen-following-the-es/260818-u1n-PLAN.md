<objective>
Rebuild the Claude Design prototype's **Summary** screen as the fifth screen of the Next.js app: a one-page dashboard that shows the whole board design at once and prints to a single landscape sheet.

Purpose: this is the sheet a shaper carries to the foam. Every number on it already exists on one of the four screens built so far — the point of the summary is seeing them together, and getting them onto paper. It is also the first screen that reveals whether the four existing views can be embedded somewhere other than their own full-width screens, which is why it leads with a tracer that puts exactly one of them into a summary card before the other four follow.

Output: a `/design/summary` route and SUMMARY nav entry; compact/embeddable variants of the five existing view components (no second implementation of any view); a board name in the shared design store; and a landscape print path with the print-only name block and the print-fit scaling.

**Not a geometry task.** Unlike quick tasks 260818-kvp / lm0 / mr2 / nyw, the Summary screen has no math of its own: the prototype's `Summary.dc.html` is layout, a text box and a print handler, and every value it shows arrives from an embedded screen. There is no `lib/geometry/summary.ts`, no golden fixture and no new test file, because there is no new calculation to pin. The pattern this task follows from those four is the *screen* pattern — shared store in, `components/<screen>/` out, nav entry, nothing persisted.

**Tracer-first.** Task 1 wires the route end-to-end with one real panel. The genuinely unknown thing here is whether a view built for a full-width screen reads sensibly at a third of the width inside a card — cheaper to learn that after one panel than after five.
</objective>

**Read the Next.js docs before writing route code.** Per `AGENTS.md`, this repo's Next.js is not the one in your training data. `app/design/summary/summary.css` is a route-scoped stylesheet — read `node_modules/next/dist/docs/01-app/01-getting-started/11-css.md` before wiring it, and `.../14-metadata-and-og-images.md` if the page metadata export differs from what `app/design/rails/page.tsx` already does.

**Deliberate simplifications from the prototype, each for a stated reason — record all three in the SUMMARY:**
1. **No height measuring.** `Summary.dc.html` runs a `ResizeObserver` + 150ms poll (`measureRootAvail`, lines 106-137) to discover its own available height, because it was embedded in an unknown shell. Our `app/design/layout.tsx` already passes flex height through to every screen, so the grid takes its height from the layout with `min-h-0 flex-1` and no JavaScript. Same result, no observers.
2. **Type scale in CSS, not JS.** The prototype computes `fontScale = clamp(0.85, 1.6, (rootAvailW / 3) / 400)` (line 161) — that is `clamp(0.85, viewportWidth / 1200, 1.6)`. Expressed per font size as `clamp(base*0.85, base/12 vw, base*1.6)` it is the identical curve in one CSS declaration, with no measurement. Worked example: the 10px compact callout becomes `clamp(8.5px, 0.8333vw, 16px)`, which is exactly 10px at a 1200px window.
3. **One cropped shared plot axis instead of three per-section crops.** The prototype crops each compact plot's x-axis separately (`cropXMin` -5 / -6.5 / -5, `Rails.dc.html` lines 1214-1216). Our rails screen deliberately shares one x-axis across the three plots so they can be compared by eye; the summary keeps that property and crops the *shared* minimum at -6.5", the widest of the prototype's three. Nose and tail therefore show a little more empty inboard space than the prototype does, and all three stay on one comparable axis.

> The browser snapshots the page as soon as the `beforeprint` handler returns. A React state update scheduled inside that handler is asynchronous and is not guaranteed to have committed by then, so the measured scale could miss the printed page entirely. Everything that must be true at snapshot time is therefore either pure CSS (`@media print`, which the browser applies natively) or set directly on the node inside the handler.
