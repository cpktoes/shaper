<objective>
Give the Summary sheet's shaded panels the theme's board-fill colour. Today they are painted
by `--order-form-shade`, the site accent at 7% over the sheet's own surface, which computes to
about `#f7fbfa` in Daylight — a wash so faint on a white sheet that the founder reads the bars
as colourless.

Purpose: `--surf-board-fill` already means "the interior wash of a board" and is calibrated
per theme. Pointing the shade at it makes the sheet's panels part of the same theming story as
the board drawings, at a strength that is actually visible.

Output: one changed declaration in `app/design/summary/order-form.css`, plus an honest rewrite
of the comment above it — the current comment ends on a contrast claim that this change makes
false, and it has to be replaced with the measured numbers.
</objective>

<already_researched>
Measured against the running app and re-derived independently here. Do not re-check any of it.

**What the bars are.** One route-scoped token at `app/design/summary/order-form.css:68` paints
every shaded element on the sheet:

```
--order-form-shade: color-mix(in srgb, var(--color-surf-accent) 7%, var(--color-surf-panel));
```

It has exactly **three call sites**, all reading `bg-(--order-form-shade)`, and the comment
above the token already names them as one family — *"logo block, spine labels, the shaper's
sub-box"*:

1. `components/summary/order-form-primitives.tsx:98` — `RailLabel`, the vertical spines
   (RIDER INFO, SURFBOARD SHAPE AND DESIGN, GLASSING, SHAPING DATA). These are the "section
   bars" the founder is pointing at.
2. `components/summary/order-form-primitives.tsx:201` — `LogoBlock`
3. `components/summary/order-form.tsx:634` — the "Shaper Use Only" `FormBox`

**The bridge alias exists — confirmed, do not go looking.** `app/globals.css:400` declares
`--color-surf-board-fill: var(--surf-board-fill);` inside the `@theme static` block that starts
at line 341. So `var(--color-surf-board-fill)` is a real, emitted custom property. Both
spellings resolve; the `--color-` one is the bridge layer the rest of this stylesheet already
uses (`--color-surf-accent`, `--color-surf-panel`), so it is the one to use here.

**Contrast — computed for all four themes, and the change is safe.** The only text sitting on
these panels is `text-surf-ink` and `text-surf-ink-muted` (verified: no other `text-surf-*`
class appears in `order-form-primitives.tsx`). Against each theme's board fill:

| theme | fill | ink on fill | muted on fill | muted on the OLD shade |
|---|---|---|---|---|
| Daylight | `#d9f2ed` | 12.30 | **5.35** | 6.02 |
| Chalk | `#d8ebf2` | 11.76 | **5.11** | 5.81 |
| Slate | `#1a2732` | 13.81 | **6.36** | 7.45 |
| Phosphor | `#142414` | 7.84 | **5.11** | 5.96 |

Every muted figure clears 4.5:1; the tightest is **5.11**, with 0.61 of headroom. The change
does spend some margin — it just does not spend all of it. This matters because the existing
comment is emphatic that the 7% figure is *"bounded by contrast, not by taste"*: a grey wash
once put the logo block's placeholder line at 4.25:1, under AA. That history is real and the
rewritten comment must keep it.

**Print behaviour changes, and it is not a regression — but it must be named.** In
`@media print`, `app/globals.css:630` pins `--surf-board-fill` to `var(--ramp-daylight-ground)`
= `#ffffff`, so the board prints hollow and does not waste ink inside the outline. Custom
properties resolve at use time, so after this change the shade token resolves to plain white on
paper. The panels therefore print with no fill.

On paper this is a near-no-op: they were already printing at `#f7fbfa`, which no consumer
printer resolves as distinct from white, and every one of these panels is delimited by its own
`border-surf-ink` outline, which the print rules explicitly preserve. So the printed sheet is
materially unchanged — but the reason is worth writing down rather than discovering later.

**Precedent that constrains the answer.** Quick task 260825-rqm changed this exact token, and
its finding was that a colour literal here cannot follow a theme (7% over a hardcoded white gave
near-white blocks on Phosphor and Slate). Whatever the new value is, it must be built from theme
tokens, and it must stay in this route-scoped stylesheet rather than migrating to `globals.css`.
</already_researched>

<decisions>
Two calls were open. Both are settled here; the executor implements, it does not re-litigate.

**1. Redefine the shared token — do not special-case the spines.** The founder said "section
bars", but the three call sites are deliberately one vocabulary, and the existing comment says
so. Tinting only the spines would leave the logo block and the Shaper Use Only box pale beside
newly-tinted bars, which reads as an inconsistency rather than as a fix. Redefining the token
keeps the family coherent and is one line. (If the founder does want spines only, see
`<standby_variants>` — it is a small, clean switch.)

**2. Point the token straight at the board fill; do not mix it into the panel.** A mix would
introduce a second tunable percentage that would need its own justification and its own contrast
budget, and it would buy nothing: `--surf-board-fill` is *already* a per-theme calibrated wash
rather than a saturated colour, which is exactly why it works as a panel ground. The direct
spelling is also literally what was asked for — the board fill, per the theme.
</decisions>
