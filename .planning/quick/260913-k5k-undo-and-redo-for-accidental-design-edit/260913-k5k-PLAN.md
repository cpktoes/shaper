<objective>
Give a shaper a way to take back the last thing they did to the board.

Purpose: every value on the five design screens is a live control — a slider that follows a finger,
a point dragged across the drawing, a number typed into a box. There is currently no way back from
any of them. A thumb that brushes the widepoint while scrolling moves the board's widest point and
the only remedy is to remember the old number and type it in again. That is a bad feeling on a tool
a shaper is meant to trust with real foam.

Output: a session history of the board's design — outline, rocker, foil, rails, fins, volume and the
import toggles — with Cmd/Ctrl+Z to step back and Shift+Cmd/Ctrl+Z to step forward on a computer,
and a pair of thumb-sized arrow buttons above the tab bar on a phone. One movement is one step back.
Nothing is saved to the database, nothing survives a reload, and nothing changes for a mouse at
desktop width.
</objective>

<honest_scope>
This is a genuinely small change with one genuinely fiddly part, and it is worth saying which is
which before anyone starts.

The easy part is the history itself: a stack of board snapshots, a second stack for redo, a cap and a
coalescing rule. It is thirty lines of pure TypeScript and it is fully testable without a browser.

The fiddly part is recording the RIGHT snapshot at the RIGHT moment inside a React store that fires
its updates dozens of times per drag. Getting that wrong in either direction is a real bug a shaper
would feel: record too eagerly and one drag becomes fifty undos; record from inside a state updater
and StrictMode's double-run records phantom steps. The shape in `must_haves.key_links` — a pending
ref set in the event handler, one effect that records after the commit — is the shape that is safe,
and it is not to be "simplified" during execution.

What this does NOT do, on purpose: it does not persist anything (a reload starts clean, as the
founder decided); it does not undo deleting a board from the rack (D-13 stands); it does not undo a
board-name edit (that is a text box, and the browser's own undo owns it); and it adds nothing to the
desktop chrome.
</honest_scope>

    type (an object with a single number field is enough — the module must never care what is in it).
    Every case fails before the module exists.

    The stacks:
    - A fresh history can neither undo nor redo.
    - Recording an edit makes undo available; undo hands back the snapshot that was recorded and
      leaves the current one available to redo.
    - Redo hands back exactly what undo took away, and returns the history to where it was.
    - Undo on an empty past returns null (no throw, no silent no-op that looks like success). Same
      for redo on an empty future.
    - Three edits then three undos walk all the way back to the first snapshot, in order.

    Redo is thrown away by a new edit:
    - Record, undo (redo now available), record a new edit — redo is gone. This is what every editor
      does and what stops a shaper stepping "forward" into a board that no longer exists.

    Coalescing — the part that makes one drag one step:
    - Two edits with the SAME key, the second within `COALESCE_WINDOW_MS`, leave exactly ONE entry in
      the past, and that entry is the snapshot from BEFORE the first of them.
    - Fifty edits with the same key, each 10ms after the last (a real drag), still leave exactly one
      entry — the window restarts on every fold, so total duration is irrelevant.
    - Two edits with the same key more than `COALESCE_WINDOW_MS` apart are two entries.
    - Two edits with DIFFERENT keys, however close together, are always two entries.
    - A null key never coalesces — two consecutive null-key edits are two entries — and a null key
      also blocks the NEXT edit from folding onto it, whatever key that next edit carries.
    - An edit immediately after an undo never folds onto the entry the undo left behind, even with
      the same key inside the window. (Undo and redo both clear the coalescing key.)

    The cap:
    - `HISTORY_LIMIT` edits leave `HISTORY_LIMIT` entries; one more drops the OLDEST, never the
      newest, and the remaining entries stay in order.

    The keyboard shortcut, as a pure decision:
    - Cmd+Z and Ctrl+Z both read as "undo"; Shift+Cmd+Z and Shift+Ctrl+Z both read as "redo".
    - An upper-case `"Z"` (what a browser reports when Shift is held) is read the same as `"z"`.
    - A bare `z`, a Cmd+S, an Alt+Cmd+Z and any other key read as null.

    The typed-field guard, as a pure decision:
    - `<input type="text">`, `<input type="number">`, `<input>` with no type at all, `<textarea>` and
      anything `contenteditable` all count as a text field the shortcut must leave alone.
    - `<input type="range">` (a slider thumb — Base UI renders one) does NOT count, and neither do
      checkbox, radio, button, submit, reset, color or file.
    - `<select>`, a `<div>`, a `<button>`, an `<svg>` and null all do NOT count.
  </behavior>
