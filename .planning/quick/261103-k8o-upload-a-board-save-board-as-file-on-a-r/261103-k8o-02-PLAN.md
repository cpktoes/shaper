**Planner's choices (each overrulable by the orchestrator):**
- PC13 — How the preview knows what is on the account: a new read-only action, `listMyBoardIds()`, answers the
  signed-in shaper's own board ids; the page works the preview out with the same pure `planImport` the import action
  runs. Not a dry-run mode of the import action, because:
  1. A Server Action takes at most 1 MB a call by default
     (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverActions.md`), and a whole
     download file can be far bigger (about 7 KB a board indented, plan 01 M1; the reader allows 20 MB). A dry run
     would send the whole file just to count it, and the import itself must already go in batches (PC16).
  2. A dry-run flag on the action that writes leaves one boolean between looking and writing. A read-only action can
     never write, and the ownership test pins it to one select.
  3. The answer is tiny: ids only, and only the shaper's own.
  4. The import action decides again on the server at the moment it writes, so a preview that has gone stale (a board
     added from another device meanwhile) can be wrong in a count, never harmful.
- PC14 — A board's `createdAt` is NOT kept from the file: both dates are the database's own, now. Why:
  - The only reader of a board's `createdAt` in the app is the next Export my designs file's order
    (`lib/account/account-data.ts`, found by grep at plan time), and nothing a shaper sees shows it.
  - The file's dates are untrusted text that would need parsing and bounding.
  - `updatedAt` must be now anyway, so the rack's Last touched and its automatic order put an imported board at the
    front. Keeping `createdAt` alone would date a row before it was ever on this account.
  - Duplicate gives a copy fresh dates too.
- PC15 — The file's board id is kept for the new row when it is free. The insert carries the id and does nothing on a
  clash; on a clash the board is inserted again with a fresh id. Why: R3 matches "already on your account" by board
  id. If every imported board took a fresh id (as Duplicate's copy does), importing the same file a second time, or
  again after a failure part-way, would add every board again, and the preview could never call them already there.
  A clash can only mean the id belongs to another account's board (a shaper importing someone else's whole file):
  the insert does nothing to it, so nothing of anyone else's is touched or revealed in the answer. Only a well-formed
  id is used (8-4-4-4-12 hexadecimal, lower-cased); a missing, malformed or repeated one reads as no id and the board
  is always added with a fresh one. Copies always take fresh ids. No database change: `models.id` already takes a
  given uuid.
- PC16 — The import goes in batches: the page sends at most `IMPORT_BATCH_MAX_BOARDS` (25) boards a call, and fewer
  when their designs' text passes `IMPORT_BATCH_MAX_CHARS` (600,000 characters). One board's design is at most
  `IMPORT_BOARD_MAX_CHARS` (64,000 characters — a real board is 4,000 to 7,500, plan 01 M1), and a file holds at most
  `IMPORT_MAX_BOARDS` (500, the rack order's own `RACK_ORDER_MAX_IDS`). The server refuses a call with more than 25
  boards as invalid. Each call is a few database round trips per board, well inside a Vercel function's time.
- PC17 — Where imported boards stand: everything one import adds (new boards and copies) stands at the front of the
  rack, the file's last board first (the export lists oldest first, so the newest-made stands first). In a rack the
  shaper has arranged, the stored order is rewritten that way after each batch, by folding the existing
  `orderWithNewBoardFirst` over the added ids (so a board saved after the last arrangement keeps its place behind them,
  exactly as a save leaves it). In a rack never arranged nothing is written: the automatic order already puts the
  newest first, as `saveModel` leaves it. A failed placement is logged and never fails the import. ASK THE FOUNDER:
  should a copy stand beside the board it copies, as Duplicate's does, instead of at the front?
- PC18 — A copy is named `boardCopyName(name)`, "Copy of " and the file's name for it — exactly Duplicate's rule —
  and `duplicateModel` switches to the same function, so the two can never drift.
- PC19 — Import my designs also takes a one-board file (plan 01's): it reads as one board with no id, so it is always
  added. Harmless and friendly; the words still speak of an Export my designs file.
- PC20 — Reading rules: plan 01's `readBoardFileContents` and `readBoardEntry` (the save reader plus the rack's
  drawing check, names trimmed and cut to 200 letters), plus PC16's caps. The file's `settings` and every other key
  are never read. A board's name for the row is its file name, or `Untitled Board` when that is empty (a saved board
  always has a name, as `saveModel` insists), and the design's own `boardName` is set to it (`saveModel`'s pinning).
  An unreadable board is reported by its name, or "board {position}" when it has none.
- PC21 — The import action, in `app/actions/account.ts` beside Export and Delete: `await auth()` first; signed out
  answers `{ imported: false, reason: "signed-out" }`; a request that is not a list of 1 to 25 boards, or whose copies
  choice is not a real boolean, answers `invalid` before any statement. Then the account's Tip Style is looked up only
  when a board holds a Phase 11 blank (`hasPhase11Blank` / `resolveCarryOverTipStyle`, exactly as `duplicateModel`
  does — a download file holds boards exactly as stored, and some may still carry a Phase 11 blank). Every board is
  re-read; the account's ids are read (owner-scoped); `planImport` decides; each write is ONE insert with `locked:
  false` inside its own try (PC15's second insert on a clash), so one bad board never rolls back another; never an
  update, never a delete; the placement (PC17); `revalidatePath("/")` when anything was added; and the answer
  `{ imported: true, added, alreadyThere, copies, failed }` with `failed` the labels of boards that couldn't be read or
  written. Nothing is logged with an account id (the file's own rule).
- PC22 — The section, in place on the page (never a pop-up — Clerk's panel keeps focus): a title, one line of body,
  "Choose a file…" (a plain button that clicks a hidden `<input type="file" accept=".json,application/json">` inside
