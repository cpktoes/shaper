## 1. The diagnosis, in ink rather than in boxes

The rider column is three flex rows in a fixed-height band:

```jsx
<div className="flex min-w-0 flex-1 flex-col justify-between gap-1 py-0.5">
  <OrderFormField label="Name" />
  <OrderFormField label="Ph #" />
  <div className="flex gap-3">
    <OrderFormField label="Height" className="flex-1" />
    <OrderFormField label="Weight" className="flex-1" />
  </div>
</div>
```

Measured live at the default preview (container 880px, band 137px tall, `py-0.5` = 2px each
side, three row boxes of 19px, `space-between` yielding two 38px gaps):

| | box top | rule | box bottom |
|---|---|---|---|
| Name | 166.5 | **185.5** | 185.5 |
| Ph # | 223.5 | **242.5** | 242.5 |
| Height/Weight | 280.5 | **299.5** | 299.5 |
| column | 164.5 | | 301.5 |

`OrderFormField` is `items-baseline`, and the ruled line is the `border-b` on the value span
— the tallest item in the row. So **the rule is the bottom edge of its row box**, every time.

Read as boxes: gaps of 38 and 38, perfectly even. Read as ink:

- band top → rule 1: **21px** (Name's writing space)
- rule 1 → rule 2: **57px** (Ph #'s)
- rule 2 → rule 3: **57px** (Height/Weight's)
- rule 3 → band bottom: **2px** (dead)

That is the defect. It is not that Ph # is mis-centred — the three rules are already on a
perfect 57/57 pitch. It is that the whole block hangs from the top, so the first field is
starved and the space that would have fed it is stranded, unusable, under the last rule.
"Recentre Ph #" is the founder describing the *consequence*: once NAME is pushed down, Ph #
has to come with it or it stops being midway.

**This is why a fix that only adds padding moves the crowding rather than removing it.** Add
`pt-4` and keep `justify-between` and the free space that padding consumes comes straight out
of the two gaps — rule 1 drops, rules 2 and 3 rise, and you have to solve for the fixed point
by hand. Do it anyway and you land on a hard-coded number that does not survive the sheet
being scaled (see section 4).

## 2. The fix — position by the slots, not by the boxes

```diff
-<div className="flex min-w-0 flex-1 flex-col justify-between gap-1 py-0.5">
+<div className="flex min-w-0 flex-1 flex-col justify-evenly">
```

Three deletions and one word. `space-evenly` cuts the column's blank space into four equal
slots `s` — one above the first row, one between each pair, one below the last:

```
s | row1 |rule1| s | row2 |rule2| s | row3 |rule3| s
```

Because the rule is the row's bottom edge, walking that strip gives:

- band top → rule 1 = `s + r`
- rule 1 → rule 2 = `s + r`
- rule 2 → rule 3 = `s + r`
- rule 3 → band bottom = `s`

**The first three are equal to each other by construction, at any size, for any row height.**
Nothing is tuned. The tail is exactly one row height less than the pitch, and that difference
is where the last rule's own label type lives — so measured as ink rather than as geometry the
block reads centred, with ~25px of clear paper above the topmost letterform and ~20px below
the bottom rule. Slightly more above than below, which is the standard optical-centring
correction: a block of type sitting dead-centre reads low.

Both `gap-1` and `py-0.5` must go, and neither is incidental:

- **`gap-1` breaks `space-evenly`.** A gap is added to the between-item slots only, never to
  the two edge slots. Left in, the four slots come out 17/21/21/17 and the top-vs-middle
  asymmetry this task exists to remove is reintroduced at a smaller size.
- **`py-0.5` is 2px of padding that stops the top and bottom slots from being real slots.** It
  is the 2px the founder measured above NAME and below HEIGHT. Removing it hands those four
  pixels back to the distribution; the column's border box is unchanged either way, because it
  is a `flex-1` child of a fixed-height band.

## 3. The numbers this produces — the acceptance test

At the default preview (container 880px, band 137px, rows 19px):

`s = (137 − 3 × 19) / 4 = 20`, so the pitch is `20 + 19 = 39`.

| | before | after | moves |
|---|---|---|---|
| band top → NAME rule | 21 | **39** | +18 |
| NAME rule → PH # rule | 57 | **39** | |
| PH # rule → HEIGHT rule | 57 | **39** | |
| HEIGHT rule → band bottom | 2 | **20** | |
| NAME rule, absolute | 185.5 | **203.5** | down 18 |
| PH # rule, absolute | 242.5 | **242.5** | **does not move** |
| HEIGHT/WEIGHT rule, absolute | 299.5 | **281.5** | up 18 |

Ph # not moving is the neat proof that this is the right shape of fix: the two outer rules
travel 18px each, symmetrically, toward the line that was always in the middle. That is
literally "Ph # recentred between Name and Height", and it is a strong single-number check.

Scale-independent form — this is the assertion that must hold, whatever width the browser
window happens to be:

```
(rule1 − col.top) == (rule2 − rule1) == (rule3 − rule2)     within 0.6px
(col.bottom − rule3) == (rule1 − col.top) − rowHeight        within 0.6px
col.height == 137 (unchanged)                                within 0.6px
```

## 4. Why not the other shape — equal gaps with the bottom kept at 2px

`justify-start` with `padding-top` and the row gap both set to the same hand-computed number
(26px) would give 45/45/45 with the 2px tail kept, i.e. a slightly roomier pitch. Rejected on
two counts:

- **It is a pixel constant on a sheet that is scaled.** The printed sheet is 733px against the
  880px preview, and `useOrderFormPrintFit` pins the container before measuring. A fixed 26px
  gap does not shrink with the sheet, so the tail absorbs all the slack — and the tail goes
  NEGATIVE at around a 610px container, which a 640px-wide browser window produces. The rider
  fields would then spill out of the header band into the drawings row. `space-evenly` cannot
  overflow until the band is shorter than three rows stacked (~286px container, narrower than
  any phone).
- **A rule 2px above the band edge is a print hazard this repo has already been bitten by.**
  260826-j97 recorded that two edges a pixel apart read smudged; at print scale that 2px is
  1.7px between a hairline rule and the band boundary the logo block's border sits on.

The pitch this costs is small in the terms that matter — printed, `space-evenly` gives a
7.8mm ruled pitch against ruled paper's usual 7-9mm, with 3.9mm clear under the last rule.
NAME goes from 4.6mm of writing space to 7.8mm.

## 5. The Height/Weight wrapper behaves exactly like the other two

Asked, and the answer is no special case. The wrapper is `<div className="flex gap-3">` in a
column-direction parent, so `align-items: stretch` acts on width, not height — the div is
sized by its content, and its content is two `OrderFormField`s carrying the same two font
sizes as the bare rows. It measures 19px, the same as Name and Ph #, and both children's rules
land on the same y (299.5 today). So it contributes exactly one rule line to the rhythm and
`space-evenly` treats it as one item, like the other two.

Its own `gap-3` is horizontal — the space between HEIGHT and WEIGHT — and stays. Only the
column's vertical `gap-1` is removed.

## 6. The safety property

`.order-form-band-header { flex: 0 0 12% }` is not touched, and nothing here can touch it: the
rider column is a `flex-1` child inside that fixed share, redistributing space that already
belongs to it. The band's height cannot change, so the drawings row below cannot move, so
`ORDER_FORM_ROCKER_BOX_PX` in `components/rocker/rocker-view-frame.ts` — whose arithmetic
explicitly cites "the header band (12%, 117.1px)" — stays valid, and the print-fit chain is
unaffected. The executor proves this by measuring, not by asserting it: the ROCKER box's
rectangle is captured before and after and must be identical.

If any step of the work would change the band's height, **stop and say so** — that is the one
outcome this task must not produce.
