<objective>
On a phone, show each order-form sheet as a true preview of the printed page — the whole sheet
shrunk as one picture to the screen's width, or at full size when the screen is wider.

Purpose: the founder's own words — "The summary page on the phone appears to resize all the boxes.
It should just show the sheet as a preview of what it will look like when it prints. It should just
auto-fit to whatever the screen's width is, or full size, whichever is smaller." Today the sheet is
redrawn at the phone's width rather than shrunk: every box, column and type size is worked out again
for a 342px-wide page, so the headings run into each other and the whole drawings row — both board
outlines, the rocker profile and the three rail sections — collapses to nothing. A shaper cannot
check on a phone what will come off the printer, because it is not the same sheet.

Output: the sheet stack is laid out at the width the form was designed for and scaled down as one
picture to whatever the screen allows; the printed page is untouched; and the Print Order Form
button stops hanging off the left edge of a phone.
</objective>

Everything below was measured at planning time in this checkout, against a dev server started from
this repo, driving the real Chromium and the real WebKit that the `android`/`desktop` and `iphone`
Playwright projects use. Nothing here is estimated. Reuse these numbers; do not re-derive them, and
do not substitute a guess for one.

## Fact 1 — what a phone shows today, and why it is a different document

At an iPhone 14 (390px) the page wrapper's own `px-6` leaves 342px, and the sheet stack takes all of
it. Because every type size on the sheet is `clamp(min, N cqw, max)` against that stack and every
column is a percentage of it, the whole sheet is re-laid-out at 342px:

| | desktop 1280 | iPhone today | Pixel 7 today |
|---|---|---|---|
| sheet box | 880 x 1159.53 | 342 x 450.63 | 364 x 479.63 |
| SHAPER wordmark type | 24.64px | **16px** (its clamp floor) | 16px |
| dimensions row type | 20.24px | **14px** (its clamp floor) | 14px |
| logo block, as a share of the sheet's width | 0.33654 | **0.36257** | 0.36257 |

The type stops at its floors while the boxes keep shrinking, and the fixed-pixel parts (the 1.5px
sheet border, the 6px sheet padding, the 24px spine, the 4px band gaps) stay put and become
proportionally huge. A screenshot taken at planning time shows the result plainly: `LENGTH`/`NOSE`/
`WIDEPOINT` overprint each other into `LENGTHOSE WIDEPOFINSET`, and the COLOR DESIGN & LOGOS panel
is a 20px-tall empty strip — both board outlines, the rocker profile and all three rail section
plots have been squeezed out of existence.

## Fact 2 — the fix, measured in both engines

The sheet stack is laid out at its design width (880px) and scaled as one picture:

| | scale | sheet painted | sheet's layout width | wordmark | dims row | sideways scroll |
|---|---|---|---|---|---|---|
| Chromium 1280 (today) | — | 880 x 1159.53 | 880 | 24.64px | 20.24px | none |
| Chromium 1280 (after) | 1 | 880 x 1159.53 | 880 | 24.64px | 20.24px | none |
| WebKit iPhone 14 | 0.388636 | 342.00 x 450.64 | 880 | 24.64px | 20.24px | none |
| Chromium Pixel 7 | 0.413636 | 364.00 x 479.62 | 880 | 24.64px | 20.24px | none |
| Chromium 900px window | 0.968182 | 852 x 1122.64 | 880 | 24.64px | 20.24px | none |

`0.388636` is exactly `342 / 880`; `0.413636` is exactly `364 / 880`. The desktop row is identical to
today in every figure, including the stack's left edge at x=200.

## Fact 3 — `zoom` is the obvious way and it is wrong on an iPhone

`zoom` shrinks the layout box for you, so it needs no height reservation, and it works perfectly in
Chromium. In WebKit it produces a different document:

| WebKit iPhone 14, sheet laid out at 880 and zoomed to 0.388636 | |
|---|---|
| wordmark | **16px** (should be 24.64px) |
| dims row caption | **12px** (should be 14.3968px) |

The cause is measurable: under `zoom`, WebKit resolves container-query units against the shrunken
size, so `2.8cqw` reads against 342 instead of 880 and drops to its clamp floor. Chromium divides
the container size back out and gets it right. Tried both ways round — the zoom on the stack itself
and the zoom on a wrapper above it — same result. **A Chromium-only check would have passed and
shipped an iPhone that still shows a different document.** `transform` has no such problem in either
engine, because it never takes part in layout.

## Fact 4 — the height the scaled stack must reserve

`transform` leaves the layout box at full size, so something has to reserve the shrunken height or
the page scrolls past a screen and a half of nothing. Measured exact, with the scaler's own bottom
edge landing on the last sheet's bottom edge to 0.00px in every case:

    two sheets:    880 * 10.37 / 7.87 * 2 + 32     = 2351.06px   (x scale)
    three sheets:  880 * 10.37 / 7.87 * 3 + 32 * 2 = 3542.59px   (x scale)

    iPhone, two sheets   -> 913.70px     iPhone, three sheets -> 1376.78px
    Pixel 7, two sheets  -> 972.48px

Every input is a number already declared: the design width, the sheet's `aspect-ratio: 7.87 / 10.37`,
the stack's `gap-8` (2rem = 32px), and the sheet count the component already computes for the
`PAGE x OF y` marks.

## Fact 5 — printing does not notice

Printed to a real PDF with headless Chromium (page geometry read back out of the file), before and
after, at a desktop viewport and at a 390px one:

| | pages | points per screen dot | sheet's printed border |
|---|---|---|---|
| today | 2 | 0.75 | 734 x 991 |
| with the preview scaler, desktop viewport | 2 | 0.75 | 734 x 991 |
| with the preview scaler, 390px viewport | 2 | 0.75 | 734 x 991 |

And the print handler writes exactly what it writes today: root `733.448px`, sheets `733.448 x
990.55px`, `zoom` 1.

## Fact 6 — the button row, and why it hangs off the left edge

The row under the paper (`Print Order Form`, `Export Template`, the instructions tick-box and its
sentence) cannot wrap, so its natural width is the sum of its parts — 915.3px. The page wrapper
centres it. On a phone that means it overhangs **both** edges equally:

| | row width | row's left edge | Print button's left edge | page scrollWidth |
|---|---|---|---|---|
| iPhone today | 433.2 | **-21.6** | **-21.6** | 436 (against a 390 screen) |
| iPhone, allowed to wrap | 342 | 24 | 56.9 | 390 |
| Pixel 7, allowed to wrap | 364 | 24 | 67.9 | 412 |
| desktop 1280, allowed to wrap | 915.3 | 182.3 | 182.3 | 1280 |

Letting the row wrap fixes the phone and changes nothing on a desktop, where it still fits on one
line. This is also the only thing making the Summary scroll sideways on a phone.

## Fact 8 — browser support for what this uses

`transform` is universal. `container-type` needs Safari 16, `@property` Safari 16.4, and `tan()`/
`atan2()` Safari 15.4 — all at or under this app's Tailwind v4 floor of Safari 16.4, which the
stylesheet's own type-scale comment already records. `tan(atan2(<length>, <length>))` is how a ratio
of two lengths is expressed as a plain number in CSS, since `calc()` will not divide one length by
another; it was verified in Chromium, WebKit and by direct probe (`calc(100px * min(1, tan(atan2(
342px, 880px))))` computes to `38.859375px` in every engine tested).
