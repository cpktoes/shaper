<decisions>
Planner's choices (Claude's discretion). Each is recorded here and cited in the task that implements it.

- **P-1: Where the Contact row sits: the first row of both menus.**
  - The phone menu is taller than a phone's screen and scrolls inside itself (quick 260926-wmf). A row placed
    last would sit below the fold.
  - At the top it is visible the moment either menu opens.
  - In the phone menu it groups with Home, the menu's other "go to a page" row: Home (hidden on `/`), then
    Contact (hidden on `/contact`), then one divider, then the settings.
  - In the gear menu it is Contact, then a divider, then the settings. On `/contact` itself both are left out,
    the same way Home is left out on `/`.
  - It is one exported component, `ContactMenuItem` in `settings-menu.tsx`. That is the file's existing
    one-definition rule, so the two menus can't drift apart.
- **P-2: /contact joins the phone-shell routes.** Today `SiteNav` shows the phone's compact top bar only on `/`
  and `/design/*`. Every other route gets the full desktop link row at every width. So without this change a
  phone on /contact would get the desktop row squeezed into 390 dots. The page also mounts `PhoneTabBar` as its
  last child, the way `app/page.tsx` does, so a phone keeps its one-tap way back to the six design screens.
- **P-3: The test stand-in** (the coordinator's suggested shape, pinned):
  - **When it can switch on.** Only when BOTH are true:
    - `nodeEnv !== "production"`. The glue passes the literal `process.env.NODE_ENV`, which Next inlines as
      `"production"` in every production build, Vercel's included.
    - `SHAPER_CONTACT_STAND_IN === "1"`. Only `playwright.config.ts`'s webServer sets it. The name follows
      `SHAPER_BLANKS_SOURCE`'s precedent.
  - **What it does when on.** The real key is NEVER used. Each test picks its outcome with a cookie,
    `shaper-contact-stand-in`:
    - `sent`: the stand-in accepts the message.
    - `failed`: the stand-in refuses it.
    - absent or anything else: no send path, so the page shows the address only.
  - **Why a cookie.** All three page states can then be proved in one dev-server run on all three projects. And
    even if a future `.env.local` carries a real key, the test server still can't send real mail.
  - **Production.** `playwright.prod.config.ts` already strips the base env, so the flag never reaches a
    production server.
- **P-4: The form keeps what was typed.**
  - React 19 resets a form's uncontrolled fields after a function `action` completes. To keep the typed text,
    every non-sent state echoes the typed values back as `values`.
  - The form is keyed on `state.attempt`, a counter the action bumps on every submission. Each answer therefore
    remounts the fields with the echoed text as their defaults, and a reset can only restore that same text.
  - The remount also lets the first field with a problem take `autoFocus`.
  - `rename-dialog.tsx` and `board-name-prompt.tsx` already use `autoFocus`.
  - The form uses the `action` prop, not `onSubmit` plus preventDefault. A tap before hydration still POSTs
    through the Server Action, and a message can never end up in a URL.
- **P-5: The field order follows the founder's own sentence:** Message, then Email to reply to, then Name
  (optional). The thing to write comes first. A signed-in shaper's email and name are already filled in.
- **P-6: `noValidate` on the form.** The friendly server messages show instead of the browser's own bubbles.
  `maxLength`, `type="email"`, `autoComplete` and `inputMode` stay, for the right phone keyboard and a hard
  typing cap.
- **P-7: The honeypot field is named `website`, labelled "Website".**
  - It sits in an `aria-hidden` wrapper with the `sr-only` class. The input has `tabIndex={-1}` and
    `autoComplete="off"`.
  - `website` is not a Chrome or Safari autofill type, so a real shaper's browser won't fill it and lose their
    message.
- **P-8: Sender and recipient both use SMTP2GO's documented `Name <address>` form:**
  `Shaper Assistant <support@shaperassistant.com>`. Reply-To is the bare address, SMTP2GO's own documented
  example. The founder's replies from Gmail "Send mail as support@" go straight to the shaper.
- **P-9: The subject is `Contact form: {who} — {excerpt}`.**
  - `who` is the name, or the reply address when no name is given.
  - `excerpt` is the message flattened to one line and cut at 60 characters with `…`.
  - The whole subject is capped at 200 characters.
  - Every control character and line or paragraph separator becomes a space before anything is joined.
- **P-10: Rate limiting is accepted, not built.**
  - Before Oct 10 the defences are the honeypot, the length caps, Next's own Server Action origin check, and
    SMTP2GO's 1,000-a-month free cap.
  - If the cap runs out, sends fail and the page points to the address.
  - The founder can remove the key at any time, which turns the page back to address-only.
</decisions>

**SMTP2GO's API, verbatim from https://developers.smtp2go.com/reference/send-standard-email and
/docs/send-an-email (checked at plan time; the executor has no web access, so this is the source of truth):**
- Endpoint: `POST https://api.smtp2go.com/v3/email/send`.
- Authentication: the header `X-Smtp2go-Api-Key: <key>`. The alternative, `api_key` in the body, is NOT used, so
  the key never sits in a JSON body.
- Required body fields:
  - `sender` (string): "The name and email address to send from, in the format `Name <name@example.com>`".
  - `to` (array of strings): "names and email addresses (up to 100) … in the format `Name <name@example.com>`".
  - `subject` (string).
- Optional body fields: `text_body` (string), `html_body` (NOT used), and `custom_headers` (array of objects,
  each with the two keys `header` and `value`). The docs say: "a `Reply-To` email can be specified here, with
  header `Reply-To` and value `name@example.com`".
- Success response (200):
  `{ "request_id": "aa253464-…", "data": { "succeeded": 1, "failed": 0, "failures": [], "email_id": "1u0SwL-…" } }`.
- Error response (400, and other non-2xx):
  `{ "request_id": "22e5acba-…", "data": { "error_code": "E_ApiResponseCodes.ENDPOINT_PERMISSION_DENIED", "error": "You do not have permission to access this API endpoint" } }`.
- Rule: a send counts as OK only when ALL of these hold:
  - the response is 2xx;
  - the JSON parses;
  - `data.failed` is the number 0;
  - `data.succeeded` is a number ≥ 1.
  Anything else counts as a failure: a non-2xx, a network error, a timeout, bad JSON, missing fields, or
  `failed > 0`.

**The exact body this plan sends:**
- `sender`: `"Shaper Assistant <support@shaperassistant.com>"`
- `to`: `["Shaper Assistant <support@shaperassistant.com>"]`
- `subject`: see P-9
- `text_body`: see Task 1
- `custom_headers`: `[{ "header": "Reply-To", "value": "<the shaper's checked address>" }]`
- There are no other keys: no `html_body` and no `api_key`.
