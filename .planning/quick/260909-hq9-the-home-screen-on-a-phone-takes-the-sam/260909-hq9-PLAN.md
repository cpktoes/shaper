<background>

## What a shaper sees today

Open the app on a phone and the first screen is the one with the board rack and the four
board-type cards. It is still drawn for a computer: the six screen links (TEMPLATE, ROCKER, RAILS,
VOLUME, FINS, SUMMARY) are squeezed onto one row across the top beside the wordmark, the gear and
the account control; the SHAPE A NEW BOARD headline is set at 30px and wraps; the page sits a
desktop 24px in from each edge with a 64px gap above the first card. Then a shaper taps a preset,
lands on TEMPLATE, and the whole app changes shape — slim bar on top, six fat tabs along the
bottom, everything thumb-sized. The home screen is the odd one out.

That was on purpose. Phase 9's brief was the five design screens; `components/site-nav.tsx:39-40`
says so in as many words ("the setup screen and the rack keep this same row at every width; that
phone treatment is Phase 10's"). The founder has asked for the layout half of it early.

## The two switches this app already has, and which one does what

`app/globals.css` declares them and CLAUDE.md's Layout section states the rule: the `shell`
breakpoint (820px) decides which LAYOUT a screen draws — `max-shell:` for the phone stack — while
the `coarse` pointer variant decides how BIG a control draws, on any width a touch device happens
to be. Width picks the layout; pointer picks the sizing; they are never conflated. Every rule in
this task is written under one or the other, never under a hand-rolled media query, and never
under a JavaScript width check.

## The three decisions this task settles

**1. Where the bottom bar is mounted.** `PhoneTabBar` must be the last child of the root layout's
flex column or it will not sit at the bottom (see `key_links`). `app/design/layout.tsx` already
does this for the design routes. `/` has no nested layout of its own, and giving it one for a
single element would be more machinery than the job needs — `app/page.tsx` returning a fragment of
its existing content followed by `<PhoneTabBar />` puts the bar in the identical position in the
identical flex chain, one import and two lines.

**2. Whether the tab bar grows a seventh HOME tab. It does not.** The bar's own comment
(`phone-tab-bar.tsx:37-41`) records the measurement: at 360px the six labels plus 2px of bar
padding a side fit with about 12px to spare, and the narrowest tab still clears 44px. A seventh
word would spend that 12px and more, and the whole bar would start scrolling the page sideways —
the exact failure phase 9 caught at 360px. So `/` mounts the same six-tab bar with no tab marked,
and the SHAPER name in the top bar stays the way home, exactly as it already is from every design
screen.

**3. What the top bar shows on `/` itself.** The same three things — SHAPER, Save, the one menu —
with one difference: the wordmark becomes plain text instead of a link, because a link pointing at
the page you are already on is a dead tap. Save is not new behaviour on this screen: the desktop
nav row already renders `SaveButton` on `/` at every width today, so this only moves it into the
phone bar. The account control is inside the one menu, exactly as D-08 put it on the design
screens.

## What must not move

- At 820px and above, the home screen is untouched: link row visible, no tab bar, 30px headline,
  32px page inset, four preset cards across. Asserted with measurements, because `/` has no
  baseline screenshot.
- The five desktop baseline screenshots must still match, with `--update-snapshots` forbidden —
  `components/site-nav.tsx` and `components/design/phone-top-bar.tsx` are shared with every design
  screen, so this task has to prove it did not disturb them.
- Every existing phone assertion about the design routes stays exactly as written; no existing spec
  file is edited.
- `lib/geometry/*`, `components/ui/*` and the design screens' own components are not touched. The
  sign-in dialog, the account menu and every Clerk flow are Phase 10's and are not opened here.

## What this leaves for Phase 10 (record this in the SUMMARY)

`.planning/REQUIREMENTS.md` lines 37-40 put the home screen and rack on a phone under **PHON-08**,
which belongs to Phase 10 ("The Whole App on a Phone"). This quick task delivers PHON-08's LAYOUT
half early at the founder's request: the two bars, the phone-sized page, and the 44px sweep over
what is visible on the home screen. Phase 10 still owns PHON-08's remaining half — the account
menu and sign-in flows opened from the home screen, the rename / duplicate / delete dialogs
(including their typed fields, which are still 32px tall on a touch screen because they come from
`components/ui/input.tsx`, off-limits here), a signed-in rack of real saved boards (which the
browser suite cannot reach signed out), and the real-device pass. The SUMMARY must say all of this
so Phase 10's planning starts from what actually landed.
