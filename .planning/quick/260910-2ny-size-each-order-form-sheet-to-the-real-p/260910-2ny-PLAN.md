<probe_gate>
## The one question, and the two branches that hang off it

Everything in RESEARCH.md is settled except one thing that no documentation answers: **does
WebKit-on-iOS resolve `100vh` and `100vw` against the real printed page area?** MDN's iOS entries
for `@page` and `beforeprint` are `"mirror"` values — inferred from desktop Safari, not measured —
and a WebKit bug comment already reports `@page` behaving differently on iOS 18.3 than on macOS
18.2. The founder's own PDF is the harder evidence, and it says his `@page { margin: 8mm }` was
ignored outright.

### The decision rule — apply it to the probe PDF, in the probe's own inch-ruler bands

Measure everything in **inch-ruler bands**, never in PDF points, so that a whole-document shrink by
iOS cannot corrupt the comparison — a shrink scales the ruler and the pitch equally, so their ratio
survives it.

1. **What is `100vh`?** Read where the `100vh` label on the left column lands against the figures in
   the inch column beside it.
2. **What is the page pitch?** Read which inch figure sits at the foot of printed page 1, and which
   sits at the foot of page 2. (The measured pitch from the founder's earlier printout was 9.101in;
   expect the probe to reproduce roughly that.)
3. **What is `100vw`?** The highest inch figure still drawn inside the width bar, and whether the
   `TODAY 7.6401in` tick is inside it or clipped away.

**Branch A — page-relative (the chosen direction, D-01).** Take this branch if `100vh` equals the
page pitch within 1%, AND `100vw` equals the printed page-area width within 1%. Then the sheet
becomes `100vw` wide and `100vh` tall (at most `calc(100vh - 1px)`), `@page { margin: 8mm }` stays
because on Blink and Safari 18.2+ it is what DEFINES the area those units read, `overflow: hidden`
on sheets becomes unconditional in print, and `use-print-fit.ts` stops deciding the size at all.

**Branch B — a phone-only box (the agreed fallback, D-03).** Take this branch if `100vh` comes back
as anything other than the page pitch — the screen viewport (compare against the `VIEWPORT:` flag
the probe prints), the full unmargined page box, or anything else. Page-relative sizing is then not
reliable on the one browser that needs it. Do NOT fall back to shrinking every sheet to the 9.10in
worst case: the founder rejected that, and Finding 5 shows it is unnecessary since desktop is
already correct (D-01, D-03). Instead:

- Desktop keeps today's `calc(min(...))` box exactly as it is — nothing about a computer's print
  changes at all.
- `use-print-fit.ts` writes a `data-print-phone` attribute onto the root **at mount**, from
  `matchMedia("(pointer: coarse)")` — a screen-time decision recorded in the DOM, so it survives
  into a print snapshot without needing `beforeprint` to fire, which is precisely the thing iOS
  cannot be trusted to do.
- A print rule scoped to `[data-order-form-root][data-print-phone] [data-order-form-sheet]` gives
  the sheet the box the probe measured — the pitch for its height, the width bar's reading for its
  width, both as literal `in` figures with the probe PDF cited in the comment beside them.
- The invariants in Task 3 change shape accordingly: the page-relative assertions become
  "the phone box's height is the measured pitch and carries no proportional multiplier", and the
  lockstep assertion becomes "the root and the sheet carry the same width in BOTH the default rule
  and the phone rule" — because the root is the `@container` every `cqw` font size resolves against
  and a drift between them silently changes the printed type size.

Under either branch, `FIT_SAFETY`'s proportional shave goes (see the second `key_links` entry), the
rocker box comment is re-scoped, and the probe page is deleted.
</probe_gate>
