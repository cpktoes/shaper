## What the fix is, and why each constraint is met

**The phone-only box is a SHAPE, not a size, applied through a DOM attribute the app writes at mount.**

`useOrderFormPrintFit` writes `data-print-touch` onto `[data-order-form-root]` when
`matchMedia("(pointer: coarse)")` matches, at mount, in screen media. One rule in `order-form.css`'s
print block, scoped to `[data-order-form-root][data-print-touch] [data-order-form-sheet]`, then gives
the sheet a shorter DEFINITE height — the same width expression the sheet already uses, multiplied by
the squarest portrait paper's own height-over-width. Nothing else changes.

### Each requirement, and how it is met

- **Desktop print unchanged.** The new rule only matches when the attribute is present, and the
  attribute is only written on a coarse pointer. Playwright's `desktop` project is a mouse, so
  `e2e/summary-print-size.spec.ts` runs against exactly the CSS it runs against today and passes on
  its current constants, with not one line of its code changed (a comment-only correction to its head
  comment is gated by a diff check that fails if any code line moves).
- **No dependence on `@page` margins.** The rule names no margin and reads no page box. It is a ratio
  applied to a width the sheet already had. iOS's own 0.579in margins are irrelevant to it — that is
  the entire point of choosing a shape.
- **No `vw` / `vh`.** Neither unit appears in the new expression, and the contract test asserts that
  against the declaration's VALUE (never the file or the rule body, so the comment above it stays free
  to explain what it replaced).
- **`beforeprint` may be used, and is.** The print proved it fires and that its DOM writes reach the
  snapshot. The handler keeps running and keeps writing the same box inline — now the touch box on a
  touch device — so the layout it measures for its overflow guard is the layout that prints.
- **Pointer, not width, and here that is not a style preference but a correctness one.** CLAUDE.md is
  emphatic that width picks layout and pointer picks sizing, and this is a sizing decision. But there
  are two harder reasons. First, in PRINT media a width query tests the PAGE, not the screen: Letter's
  printable width is about 755 dots, so `@media print and (max-width: 820px)` would match on a
  computer and wreck the very thing D-01 protects. Second, an iPad is a coarse pointer on a wide
  screen and runs the same WebKit print path as the iPhone — any width condition would exclude
  precisely the device that most needs the fix. Pointer alone, and it is read in SCREEN media at mount
  where `pointer` has a well-defined meaning, then recorded in the DOM so the print rule never has to
  ask a printer what kind of pointer it has.
- **A DEFINITE height on every sheet.** The rule declares `height` outright, in absolute units, exactly
  as the existing desktop rule does. The `fr` bands go on dividing a definite number and never go
  content-proportional. This is the non-negotiable from `use-print-fit.ts`'s head comment and it is
  preserved unchanged.
- **Forced pages (D-03).** The existing `break-after: page` on every sheet but the last stays exactly
  as it is, and an adjacent-sibling `break-before: page` is added beside it, so the break between two
  sheets is asked for from both sides. Two forced breaks at one break point combine into one break.
  The new browser test counts the PDF's real pages, so if any engine disagrees, the count says so.

### The arithmetic of the ratio

    today's sheet          733.438 x 990.547 px      ratio 1.350553   (measured, Chromium + WebKit)
    this iPhone's page       7.34in x   9.82in       ratio 1.3379     (measured, the founder's print)
    Letter @ 0.579in         7.342  x   9.842        ratio 1.34051
    CHOSEN  min(11 / 8.5, 11.69 / 8.27)              ratio 1.294118   -> 733.438 x 949.156 px

`min(11 / 8.5, 11.69 / 8.27)` is the squarest of the two portrait papers, which is US Letter. It is
chosen over "the measured 1.3379, less a bit" because it carries a proof instead of a fudge: for a
portrait page W x H with a uniform margin m on all four sides, the printable box's ratio is
`(H - 2m) / (W - 2m)`, and because H > W that value is at or above `H / W` for every m from zero
upward. A sheet shaped like the paper therefore fits inside whatever uniform margin that browser and
printer choose, which is the only sane target when the browser ignores ours and picks its own.

    headroom on the measured device   1.294118 vs 1.3379   =  3.3% to spare
    printed, after Safari's own shrink 7.342 x 1.294118    =  9.50in of sheet in 9.82in of page
    cost, and only on a touch device   949.156 / 990.547   =  4.18% shorter

The proof is not unconditional, and the plan says so rather than overselling it: with NON-uniform
margins it holds iff the two side margins together are at least `W / H` = 0.7727 of the top and
bottom margins together. The measured device's uniform margins give 1.0 against 0.7727. If some
future printer with a fat bottom margin falls outside that, the lever is this one ratio and nothing
else in the fix has to move.

### What is NOT done, and why

- **No proportional shave is removed.** The old plan banned `FIT_SAFETY`'s 0.995 because RESEARCH.md's
  Finding 1 inferred that iOS slices a continuous ribbon, which would make a proportional shave
  accumulate. The print disproves that inference outright — iOS fragments and honours breaks like
  everyone else. `FIT_SAFETY` is part of the desktop box the e2e gate measures, so it stays exactly
  where it is (D-01). The touch height does not use it: it does not need one, having 3.3% of headroom
  by construction.
- **The `zoom` overflow guard stays.** Deleting it would change how a computer prints an over-full
  sheet, which D-01 forbids. It is instead taught the touch box, so on a phone it measures against the
  height that actually applies rather than a desktop page's.
- **Nothing single-sources the printed size.** That was Branch A's idea and it died with the
  measurement. The stylesheet and the hook go on mirroring each other, and
  `components/summary/order-form-print.test.ts` goes on being the thing that fails when they drift —
  which is the only reason it is worth having.
- **`@media print and (aspect-ratio: ...)` was considered and rejected.** It would discriminate iOS
  neatly IF print media queries read the same screen viewport that `vh` turned out to read. The probe
  measured viewport UNITS, not media queries. That is an inference, not a measurement, and this plan
  does not build on inferences any more.
</mechanism>
