<mechanism>
## What the fix is, and why each constraint is met

**The touch sheet takes its WIDTH FROM THE PAGE and its SHAPE FROM THE PAPER. The print handler says
nothing at all on that path.**

Two declarations in `order-form.css`'s print block, both scoped to the `data-print-touch` attribute
the app already writes at mount:

    [data-order-form-root][data-print-touch]                             width: 100%
    [data-order-form-root][data-print-touch] [data-order-form-sheet]     width: auto
                                                                         height: auto
                                                                         aspect-ratio: 8.5 / 11

The root's `width: 100%` resolves against `[data-order-form-page]`, whose print padding is already
zeroed, whose own width comes from the design layout's full-width column, and whose width in print
media is the page area. The sheet is a flex item of the root and `width: auto` stretches it to that
same width. `aspect-ratio` then derives the height. Nothing in either rule is an inch, a millimetre,
a pixel, a viewport unit or a percentage of a height — which is precisely the property the founder's
second print says the sheet must have.

### Each constraint, and how it is met

- **The desktop path does not change at all (D-01).** Both rules match only when the attribute is
  present, and the attribute is only written on a coarse pointer. Measured at plan time in both
  engines: with no attribute the sheet's box is 733.438 x 990.547 px, ratio 1.350554, in screen and
  print media alike — byte-identical to today and to `e2e/summary-print-size.spec.ts`'s constants.
  That spec is not edited at all this time.
- **A DEFINITE height survives.** This is the non-negotiable from `use-print-fit.ts`'s head comment:
  the sheet's bands are `flex` and they must divide a real number rather than going
  content-proportional. `aspect-ratio` on a definite width yields a definite height, and that was
  MEASURED at plan time in both engines at four different page widths — the two flexible bands came
  back identical to a thousandth of a pixel every time, and `scrollHeight` equalled the sheet's own
  height. It is also the mechanism the sheet already uses on screen (`aspect-ratio: 7.87 / 10.37`),
  so it is proven in production as well as in the probe.
- **The `@container` moves, and that is faced rather than hidden.** The root is what every `cqw` type
  size resolves against, so a page-relative root means the container width changes on a phone. The
  arithmetic is in `must_haves.key_links` and the number is measured in Tasks 10 and 11 before the
  founder is asked to print. The short version: a container-relative size prints at
  `72 x px x P / C` points, which for the smallest token is a flat **8.65pt for any page area at or
  above 733.44 CSS px**, rising above 9pt below that as the 12px clamp floor takes over. 8.65pt is
  the worst case and it is not a type decision — it is the 3.8% by which the founder's usable paper
  (7.347in) is narrower than a computer's (7.640in) once Safari takes its own margins. His whole
  sheet is a 96.2% photograph of a computer's; the type is 96.2% along with it.
- **The handler writes nothing on the touch path.** `beforePrint` sets `data-printing`, reads the
  attribute off the root — never the media query a second time, keeping the discipline the shipped
  code established — and returns. There is no inline write to disagree with the stylesheet, and the
  `zoom` overflow guard cannot fire spuriously because it does not run. Pinning a px width there
  would re-impose from inside the app the exact absolute width iOS refuses to honour.
- **Overflow on the touch path is CLIPPED, not scaled, and Task 11 proves it never happens.** With no
  `zoom` guard, the unconditional `overflow: hidden` backstop is what catches content that cannot
  compress. That is why Task 11's sweep must find the narrowest page width at which every sheet still
  satisfies `scrollHeight <= clientHeight`, with the Rail Band Instructions sheet on, and report it.
- **Forced pages (D-03) are untouched.** The per-sheet `break-after: page`, the `:last-child` reset
  and the adjacent-sibling `break-before: page` all shipped in Task 4 and all stay.
- **Pointer, not width, unchanged and still correct.** In PRINT media a width query tests the PAGE,
  not the screen — Letter's printable width is about 755 dots, so a `max-width` print query would
  match on a computer and wreck D-01. And an iPad is a coarse pointer on a wide screen running the
  same WebKit print path, so any width condition would exclude the device that most needs the fix.

### Why `8.5 / 11` and not the derived `max()`

The shape does not change: `8.5 / 11` is US Letter, the squarest of the two portrait papers, and the
proof behind it is the same one that picked it before — a sheet shaped like the paper fits inside any
uniform margin the browser chooses. Under the new mechanism the proof gets simpler, because the
sheet's width IS the printable width: it fits iff the printable box's height-over-width is at least
1.294118, and every uniform margin on Letter satisfies that. On the founder's own measured page,
1.3367 against 1.294118 — 7.347 x 9.509in of sheet inside 7.347 x 9.821in of page, 0.31in of white
at the foot. **That headroom is now a property of the paper and cannot be wrong**, where the shipped
fix's headroom depended on iOS's shrink factor being what we thought it was.

A derived `aspect-ratio: max(8.5 / 11, 8.27 / 11.69)` was measured at plan time and DOES work in both
Playwright engines. It is deliberately not used. This project already has a documented case of
shipping Safari disagreeing with Playwright's WebKit on a CSS math function, the founder has exactly
one print left (D-06), and a two-number ratio has been bedrock everywhere since 2021. The derivation
does not disappear with it — `order-form-print.test.ts` works out which of `PORTRAIT_PAPER_IN`'s
papers is squarest and asserts those two exact figures, so the stylesheet stays dumb and the two
files still cannot drift.

### What was considered and rejected

- **A squarer ratio calibrated to the measured 1.1413 shrink.** Rejected in `PROBE-READING-2`: it
  needs a ratio at or below 1.1264, 13% squarer than the paper, visibly distorting the form and
  calibrated to one phone's margins.
- **`max-width` capping the touch container at the design width.** Tested arithmetically at plan
  time: it does not help a fixed-px type size by even a hundredth of a point, because it shrinks the
  printed sheet by exactly the same factor it shrinks the container — while making everything else on
  the sheet 10% smaller. Strictly worse.
- **Laying the sheet out at the design width and shrinking the picture with `transform`,** the way
  the on-screen phone preview does. `transform` does not take part in layout, so the printed page
  would still reserve an absolute 733.44px of layout box — the very thing iOS overflows — and
  pagination would be computed against a box nothing is drawn in.
- **Raising the touch path's `cqw` coefficients by 7.640 / 7.347 so the printed type matches a
  computer's exactly.** That is a fudge calibrated to one phone's margins, in a second place, for a
  4% difference nobody would see.
- **Removing `FIT_SAFETY` or the `zoom` guard.** Both are part of the desktop box the e2e gate
  measures. They stay (D-01). The touch path simply never reaches either.
</mechanism>
