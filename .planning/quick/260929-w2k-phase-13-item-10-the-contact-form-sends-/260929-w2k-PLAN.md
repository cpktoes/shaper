Phase 13 item 10, the sender swap (quick 260929-w2k): the Contact form sends through **Resend**, not the
cancelled service it was built on in quick 260929-u1t.

Purpose: the founder cancelled the old sending service and moved support@shaperassistant.com to Zoho Mail's
free plan. That plan has no way for an app to send mail. So the live Contact page is address-only today. The
founder chose Resend (free forever: 3,000 emails a month, 100 a day). With this change in place, the founder
only has to verify the domain in Resend and put one key into Vercel. After that, a shaper's note arrives in
the support@ inbox, and the founder's Reply goes straight back to that shaper. Until the key is there, nothing
about the page changes.

- `lib/contact-server.ts` reads `RESEND_API_KEY`.

<decisions>
Planner's choices. Each one is cited in the task that implements it.

- **W-1: The names.**
  - `ResendSendBody` (type) and `buildResendRequest` (builder) in `message.ts`.
  - `RESEND_SEND_URL` and `sendWithResend` in `delivery.ts`.
  - The `ContactDelivery` kind becomes `"resend"`.
  - All other exported names stay exactly as they are, including `CONTACT_SENDER`, `CONTACT_RECIPIENT`, the
    stand-in constants, `deliverContactMessage` and `submitContact`.
- **W-2: The plain-address recipient (amends P-8's `to`).** `CONTACT_RECIPIENT`'s value becomes
  `CONTACT_ADDRESS`, the bare `support@shaperassistant.com`. `CONTACT_SENDER` keeps the
  `Shaper Assistant <support@shaperassistant.com>` form, which Resend documents for `from`. `reply_to` is a
  single string, not an array (Resend accepts either).
- **W-3: Three request headers, exactly these:**
  - `Authorization: Bearer <key>`
  - `Content-Type: application/json`
  - `User-Agent: shaper-assistant/1.0`

  The User-Agent is a plan-time addition to the coordinator's pinned list. Resend's API introduction
  (https://resend.com/docs/api-reference/introduction, fetched 2026-09-29) says: "All API requests must include
  a `User-Agent` header. Requests without this header will be rejected with a `403` status code". Node's own
  fetch sends a default, but naming it removes the doubt. It is declared once, as the exported constant
  `CONTACT_USER_AGENT` in `delivery.ts`. There is no `Accept` header and no `Idempotency-Key`: the form's
  `attempt` counter already makes each Send one request.
- **W-4: The success rule (replaces the old four-part rule).** A send is OK only when all of these hold:
  - `response.ok` (2xx);
  - `response.json()` resolves to a non-null, non-array object;
  - that object's `id` is a string of length > 0.

  Anything else is a failure. On a failure there is exactly one
  `console.error("Shaper: contact message did not send", { status, errorName })`.
  - `status` is the HTTP status, or `null` when fetch threw.
  - `errorName` is Resend's own `name` field when the parsed body carries it as a string, else `null`.

  Resend's `message` field is never logged. Its validation messages can echo addresses and field values.
- **W-5: The timeout is proven, not assumed.** `sendWithResend` keeps `signal: AbortSignal.timeout(10_000)`. A
  test spies on `AbortSignal.timeout`, checks the call with `10_000`, and checks that the returned signal is the
  one handed to fetch. A second test has fetch reject with a `DOMException` named `TimeoutError` (the way a
  real timeout surfaces) and checks that it fails. There is no real 10-second wait: Node's
  `AbortSignal.timeout` ignores vitest's fake timers.
- **W-6: Raw fetch, no SDK.** The `resend` npm package is NOT installed. One `fetch` with an injectable
  `fetchImpl` keeps the sender testable exactly the way it was, and adds no dependency, so no package
  legitimacy gate applies.
- **W-7: No touched file names the cancelled service, not even as history.** The history lives in `.planning/`
  (13-SPEC.md item 10, the 260929-u1t plan and summary). Comments describe what the code does now. The same
  goes for the founder's old personal mail app: replies now come from Zoho Mail, so comments say "the
  founder's Reply" or "Zoho Mail". Where a comment cites the free-plan cap (P-10's defence), it now says
  Resend's 100 a day and 3,000 a month.
</decisions>

**Resend's send-email API (https://resend.com/docs/api-reference/emails/send-email, checked 2026-09-29/30 by
the coordinator and again at plan time). The executor has no web access, so this is the source of truth:**
- Endpoint: `POST https://api.resend.com/emails`.
- Headers: `Authorization: Bearer <key>` and `Content-Type: application/json`, plus `User-Agent` (W-3).
- Body fields used:
  - `from` (string, required). The "Name <address>" form is documented.
  - `to` (string or string[], required).
  - `subject` (string, required).
  - `text` (string).
  - `reply_to` (string or string[]).

  Nothing else, and never `html`.
- Success: a 2xx whose JSON is like `{ "id": "49a3999c-0ce1-4ea6-ab68-afcd6dc2e794" }`.
- Errors: a non-2xx whose JSON carries `statusCode`, `message` and `name`, for example
  `{ "statusCode": 422, "message": "Invalid `to` field...", "name": "validation_error" }`, or a 403 with
  `"name": "validation_error"` when the domain isn't verified yet.
- Free plan: 3,000 emails a month, 100 a day. The rate limit is 10 requests a second per team.
