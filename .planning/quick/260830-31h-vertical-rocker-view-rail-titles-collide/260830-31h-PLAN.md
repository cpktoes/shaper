## 0. The root cause, stated exactly — and one correction to the brief

Quick task `260830-2dy` reserved each title's room with `railLabelBandDepth(orientation)` =
`RAIL_LABEL_GAP + maxCardPinScale(orientation) * RAIL_LABEL_SIZE + RAIL_LABEL_EDGE_GUTTER`. That is
the type's CAP HEIGHT. It is the right measurement nose-left, where the word's cap points across the
rail and its run lies along the rail. Nose-up the title is counter-rotated by `Upright` so it reads
upright on screen, and a counter-rotated run presents its **run length** across the rail instead —
about 150 units where 25 were reserved. Exactly the axis-swap this module already documents for
cards (`cardBandDepth` uses `STATION_CARD_HEIGHT` nose-left but `STATION_CARD_WIDTH` nose-up); the
title band was written without it.

The arithmetic reproduces the founder's measurement to the pixel, which is how we know the model is
right: the deck card's far edge measures 507; the title anchor is `RAIL_LABEL_GAP` (8 units) beyond
it at 510.3; the measured word is centred at 510.5. One unit of user space is 0.407 screen px here
(the card is 64px wide and `maxCardWidth` is 156.46 units). Half the word's ~150-unit run therefore
reaches back 30px over a card whose edge is 3px away, and forward past a frame edge that is 18px
away. Both failures fall straight out of one number.

**One correction to the brief, because the test depends on it.** The brief reasons that putting the
title above the Center card makes its run lie "PARALLEL to the rail (along the long axis)". It does
not — the title still reads left-to-right on screen, and nose-up the rail runs top-to-bottom, so the
run stays ACROSS the rail no matter where along the rail it sits. **The founder's fix is still
exactly right, for a different reason:** moved onto the rail's own centre, the run no longer has to
fit in a 37-unit outboard reserve — it shares the card COLUMN, which nose-up is `maxCardWidth` =
156.46 units wide, because a rotated card presents its width across the rail. The longest title
needs 155.3 units by a deliberately generous bound. It fits inside its own column. That is the whole
fix, and it is why the containment test below measures the run against the column, not against the
long axis.

## 1. Nose-up anchors: on the rail's own centre, one card-half plus a gap toward the nose

Nose-up the content group carries `rotate(90)`, so canonical `(x, y)` lands on screen at `(-y, x)`.
The consequence worth writing down, because it is what makes this bug easy to reintroduce: **the two
anchor fields swap roles between orientations.** Nose-left `deckLabelY` is a text BASELINE and
`labelStationX` is the horizontal CENTRING. Nose-up `deckLabelY` becomes the horizontal centring and
`labelStationX` becomes the baseline.

So nose-up:

- `deckLabelY = deckRailY` and `bottomLabelY = railY` — the rails' own anchors, which nose-up are
  already documented as "the card's cross-axis centre". The title therefore centres on exactly the
  column its cards sit in, with no new arithmetic at all.
- `labelStationX = PAD_X + boardSpan / 2 - cardHeight / 2 - railLabelSize * RAIL_LABEL_STATION_GAP_EM`
  — the middle station, back off by the Center card's own half-height (its extent along the station
  axis) and then by the gap. Nose is up, so subtracting moves the word up the screen.

**LIVE card values here, not the ceiling** — a deliberate departure from `260830-2dy`'s ceiling
anchoring, and the reason matters: the title heads those cards, so it must move WITH them when the
pin changes, or it sits visibly off-centre from the column it names whenever the live scale is under
the ceiling. Frame invariance is not lost by this, because the FRAME is still derived only from
ceiling values — nothing in `minX/minY/width/height` reads `labelStationX`. Containment is then
proved at the ceiling, which is the worst case for every one of these terms.

Nose-left keeps its current expressions byte for byte.

## 2. How far above the card: a gap in EMs, not units

`RAIL_LABEL_STATION_GAP_EM = RAIL_LABEL_GAP / RAIL_LABEL_SIZE` (= 2/3), applied as
`railLabelSize * RAIL_LABEL_STATION_GAP_EM`.

The founder's question — why not a fixed gap — has a precise answer. Nose-up both the card and the
title are pin-scaled: `appliedScale` is chosen so that pinned type lands on a constant number of
screen pixels. A bare 8-unit gap between two pinned objects would NOT hold a constant on-screen
size; it would grow and shrink with the frame fit while the two things it separates did not, so the
heading would drift toward and away from its own card as the panel changed. Expressed as a share of
the title's own type size it rides the same pin and holds still.

The ratio is not chosen freely: it is exactly what `RAIL_LABEL_GAP` already is as a share of
`RAIL_LABEL_SIZE` nose-left, so a title sits the same fraction of its own type clear of its cards in
both orientations. At the vertical ceiling that is 16.9 units, about 7 screen px — visually the same
gap the approved horizontal view already shows.

## 3. Does the title need a long-axis reserve nose-up? No — but the neighbour check is the point

It sits between the Center card and the Nose @ 12in card, both mid-drawing, so no frame edge is in
play. The real question is whether it now collides with Nose @ 12in instead. Proved, not assumed:

- Space needed, at the ceiling: `maxCardHeight / 2` (37) + gap (16.9) + cap (18.3) +
  `maxCardHeight / 2` (37) = **109.2 units**.
- Space available: `(lengthIn / 2 - 12) * scale`, and under `fitToBoard` `scale` is `820 / lengthIn`,
  so this is `410 - 9840 / lengthIn` — **smallest at the SHORTEST board**: 246.0 units at 5'0",
  283.8 at 6'6", 328.0 at 10'0".
- Worst-case clearance: **136.8 units (~56 screen px) at 5'0"**.

**Note the trap.** The brief says the 12in station pitch is narrowest on a 10'0" board. True — of the
TIP pitch, which is what `maxCardPinScale` is derived from. The span that matters here is the
opposite one, Center to @ 12in, and it is tightest at the SHORTEST board. Picking the wrong extreme
would give a test that passes on a case that was never tight. The test sweeps the whole of
`LENGTHS_IN` so neither end can be missed.

## 4. `railLabelBandDepth` becomes orientation-shaped, and nose-up its zero is DERIVED

Nose-left the title genuinely stacks outboard of the rail, so the band stays exactly what it is
today: `RAIL_LABEL_GAP + maxCardPinScale("horizontal") * RAIL_LABEL_SIZE + RAIL_LABEL_EDGE_GUTTER` =
24 units (the horizontal ceiling is provably exactly 1).

Nose-up nothing stacks outboard any more, so there is nothing to reserve — but returning a hardcoded
`0` would be the same class of mistake this task is fixing: a number asserted rather than derived.
Instead the function returns the part of the title's run that its own column and gutter do NOT
already cover:

- half the longest title's run at the vertical ceiling: **77.6 units**
- half the card column plus `CARD_GUTTER`: **86.2 units**
- overhang: **-8.6**, so the band is **0** — and if a title were ever renamed to something longer,
  the frame would grow to hold it instead of the word escaping.

The run bound comes from a new `railLabelRunWidth(text, size)` using
`RAIL_LABEL_EM_ADVANCE` (0.6, this face's widest glyph at this weight) plus
`RAIL_LABEL_TRACKING_EM` (0.08, the `letterSpacing` the title is actually set with). Deliberately
generous for mixed-case words, which are narrower than digits: the measured word is ~150 units and
the bound calls it 155.3. An estimate that errs wide is the safe direction for a containment proof.
It is its own constant rather than a reach into `COMPACT_CHAR_ADVANCE`, which belongs to the order
form's digit-only readings — the same separation `RAIL_LABEL_CAP_RATIO` already keeps.

**What the vertical frame hands back:** `crossFar` and `crossNear` each lose their
`railLabelBandDepth` term, so the nose-up cross axis narrows by 74.7 units (~13%). Be honest about
what that buys: the nose-up drawing is bound by its LONG axis (the maximisation suite pins the board
at 88%+ of it), so the board most likely does not get bigger — the empty margin down each side goes
away instead. Reclaiming it is still right: reserving room for something that is not there is what
made the horizontal frame taller than it needed to be, and the nose-up frame stops lying about its
own contents.

## 5. The two words move into the layout module

`RAIL_LABEL_TEXTS = { deck: "Thickness", bottom: "Rocker" }`, exported from
`rocker-view-frame.ts` and read by the viewer. They are still byte-identical to the sidebar sections
(`rocker-controls.tsx`) and the DATASHEET row groups (`rocker-datasheet.tsx`) — one vocabulary, per
`260830-2dy` section 4, unchanged. The move exists because section 4's containment proof is now a
proof about these specific strings: the module has to know what it is proving room for, and a word
that lives in the viewer could be renamed without the layout ever noticing.

## 6. What proves the print path is untouched

Nothing on the compact or none paths is edited, and the viewer still draws titles only under
`callouts === "full"`. The existing characterisation pin from `260830-2dy`
(`rockerViewLayout — print-path characterisation pin`, holding the exact compact/none `viewBox`
literals) stays in place **completely untouched** — not re-captured, not adjusted. That it stays
green with no edit is the proof.
