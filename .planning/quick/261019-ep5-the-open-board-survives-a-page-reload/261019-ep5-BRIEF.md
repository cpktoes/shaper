# Brief — the open board survives a page reload (quick 261019-ep5)

Written by the orchestrating session on 2026-10-19 from a verified diagnosis. Everything below was
checked against the code at commit fad05d4f; the planner should trust it but re-read the files it names.

## The problem, in the founder's words

"Somehow, I keep ending up on a board without a blank and a pretty lame looking foil."

## Diagnosis (verified on the dev server)

The board being designed lives only in React state — `DesignProvider` in
`components/design/design-store.tsx`, mounted once in `app/layout.tsx`. Nothing writes it to the browser
or the address bar; only PREFERENCES are persisted (`components/units-provider.tsx`,
`fit-defaults-provider.tsx`, `saved-blanks-provider.tsx`, `starred-blanks-provider.tsx` — each keeps its
value in localStorage, with a server handoff cookie for first paint). So every FULL page load starts
`DEFAULT_DESIGN_STATE`: the stock 6'0" × 19" × 2 1/2" board, `blank: null`, the stock five-station foil and
hand-set rocker. That stock board is exactly the "no blank, lame foil" board.

Full loads happen often:

1. After EVERY deploy to main, Next's router hard-reloads an already-open tab on its next screen change,
   because the server's build id differs from the client's
   (`node_modules/next/dist/client/components/router-reducer/fetch-server-response.js`, the
   `getNavigationBuildId` check → `doMpaNavigation`). The founder deploys several times a day.
2. A phone's Safari reloads a backgrounded tab.
3. A bookmark, a refresh, or typing a /design/* address.

Saved boards are safe in the rack. It is the OPEN board (and any edits since the last autosave) that is lost.

Reproduction: home → START SHAPING on the Fish → ROCKER shows the blank `US Blanks 5'10"RP`; load the same
address again → "Pick a Blank", stock figures.

## What to build

Make the board a shaper is working on survive a full page load, so a reload, a new deploy or a phone tab
refresh brings back the same board — its blank, foil, name, fin settings, everything — instead of the
stock board. One quick task, one plan, 1–3 tasks.

### 1. A pure helper under `lib/models/` with unit tests

A new module, suggested name `lib/models/open-board.ts` (follow `lib/models/banner-dismissal.ts` and
`lib/models/autosave.ts` for style: a doc comment explaining the rule, exported constants, pure functions,
storage helpers guarded by try/catch so they run in a node test with no `localStorage` global).

- `OPEN_BOARD_STORAGE_KEY` — one app-named localStorage key, e.g. `"shaper-open-board"`. (The existing
  keys are `shaper-units`, `shaper-fit-defaults`, `shaper-sign-in-banner-dismissed`,
  `shaper-toolbar-tip-dismissed`, the starred/saved blanks keys. Must NOT contain the word "zoom" —
  `e2e/viewer-zoom.spec.ts` asserts no storage key or value matches /zoom/i.)
- The copy's shape: a small envelope with its OWN version number (so a later change can be read
  forgivingly), holding `snapshot` — exactly what `buildSnapshot(designSnapshotFields)` from
  `lib/models/design-snapshot.ts` produces for a save (nothing new serialised by hand) — plus the session
  bookkeeping that is NOT in a snapshot: `modelId` (string | null), `ownerId` (the Clerk user id the row
  belongs to, string | null), `locked` (boolean), `dirty` (boolean). `boardStarted` is implied true: the
  copy is only ever written for a started board (see §2), so a restored board is always started.
- A reader that NEVER throws: `parseOpenBoardCopy(raw: string | null, options?)` → the copy or `null`.
  JSON that fails to parse, a wrong shape, an unknown version, or a snapshot `parseSnapshot` rejects → `null`
  and the stock board stays. The snapshot inside is validated THROUGH `parseSnapshot` (which already
  tolerates older snapshot versions, drops malformed wings/starts/rockers, bounds the board length, and
  carries a Phase 11 blank over — pass `ParseSnapshotOptions` through so the store can hand it the shaper's
  Tip Style default if it wants, or just use the default). A `modelId` without a non-empty `ownerId` is
  read as `modelId: null` (a saved board always has an owner; a copy that claims otherwise is not trusted).
- A writer `openBoardCopyJson(fields: DesignSnapshotFields, bookkeeping)` → string.
- Storage helpers `readOpenBoardCopy()`, `writeOpenBoardCopy(json)`, `clearOpenBoardCopy()` with the app's
  usual fallback: `localStorage` inside try/catch, and a module-level page-memory copy
  (`blockedStorageRaw` as in `components/saved-blanks-provider.tsx`) so a browser that blocks storage
  still keeps the board for the life of the page.
- A pure owner rule, e.g. `reconcileOpenBoardOwner(copy, userId)` or similar, that answers: given the
  copy's `modelId`/`ownerId`/`locked` and what Clerk currently reports (`undefined` = not loaded yet,
  `null` = signed out, a string = that account), does the board keep its row? Keep while Clerk is not
  loaded or the shaper is signed out (never clear a saved board's copy on sign-out alone) or the account
  matches; DROP `modelId` (and `locked`, which belongs to the row) when a DIFFERENT account is signed in —
  the board stays open as an unsaved board. (`saveModel` in `app/design/actions.ts` is already
  ownership-scoped server-side — `where(eq(models.id, modelId), eq(models.clerkUserId, userId))` — and
  throws "Couldn't find that board." on a foreign row, so nothing can be written to another account's row
  either way; the client rule just stops the store from trying and showing a failed save.)

Unit tests (`lib/models/open-board.test.ts`, vitest, node environment): a round trip through write → parse
returns the same fields; corrupt JSON, a wrong shape and an unknown version are ignored (`null`); a copy
whose snapshot fails `parseSnapshot` (e.g. a board length far outside range, see
`SNAPSHOT_BOARD_LENGTH_MM`) is ignored; a copy from an OLDER snapshot version follows `parseSnapshot`'s own
rules (e.g. version 1 with no rocker/foil backfills, exactly as `design-snapshot.test.ts` shows); modelId
without ownerId reads as null; the owner rule's table (not loaded / signed out / same / different); the
storage helpers with a fake localStorage (copy `banner-dismissal.test.ts`'s `fakeSessionStorage` pattern)
and with no global at all.

### 2. The store: write the copy, read it back once

In `components/design/design-store.tsx` (read its header comment and `DesignState` first — the store's
rules about effects, StrictMode and refs are documented there and must be respected):

**Write.** An effect that runs whenever `designSnapshotFields` (identity changes only when contents do),
`state.modelId`, `state.locked` or `state.dirty` change. While `state.boardStarted` is false it does
NOTHING (a never-touched board has nothing to keep, and must not be written: D-19 — an unstarted board's
foil tips follow the live tip defaults, and a copy would bake them in). Otherwise it debounces (a short
constant in the helper, ~250 ms is plenty — a slider drag fires many updates a second) and writes
`openBoardCopyJson(designSnapshotFields, { modelId, ownerId, locked, dirty })`. Keep the latest pending
copy in a ref and FLUSH it synchronously on `pagehide` and on `visibilitychange` → `"hidden"` — a phone
backgrounds a tab without warning, and a `page.reload()` fires pagehide — so no debounce window ever
loses the last edit. localStorage writes are synchronous and the copy is a few KB; that is fine.

**Owner.** `useAuth()` from Clerk gives `userId` (undefined while loading, null signed out). Keep a ref of
the account the open row belongs to: set it from the copy on restore, and from `userId` whenever a signed-in
shaper's board has a `modelId` and no owner is known yet (a board is only ever saved while signed in —
`markSaved`, `applyModel` from the rack). When `userId` is a string that differs from the known owner, drop
`modelId` and `locked` (set `lockedRef.current = false` too) — the pure rule from §1 decides, the effect
only applies it. When `modelId` becomes null (the rack deleted the open board, `setModelId(null)` in
`components/setup/board-rack.tsx`), forget the owner.

**Read.** On the provider's first mount in the browser, read the copy ONCE in an effect (guarded by a ref
so React's StrictMode double-invocation applies it once; the apply is idempotent anyway) — never during
render and never in a `useState` initialiser: the server HTML and the first client render must agree (the
store cannot use a server handoff cookie the way the preference providers do; a board is far too big for a
cookie). A brief first frame of the stock board before the restored board appears is accepted. Restore it
the way `applyModel` does (spread `DEFAULT_DESIGN_STATE`, then every snapshot field, `boardStarted: true`)
but with the copy's own `modelId`, `locked` and `dirty`: keeping `modelId`/`locked` is what lets a saved
board keep autosaving to its row, and keeping `dirty` is what makes an autosave that never flushed before
the reload run now (the existing autosave effect does the rest once Clerk confirms the session). Set
`lockedRef.current`, the owner ref, `pendingEditKeyRef.current = undefined` and an empty history — the undo
history is session-only by design and starts empty. Nothing parses twice: `parseOpenBoardCopy` already ran
`parseSnapshot`.

The history-recording effect must NOT record the restore as an undo step: it skips when no pending edit
key is set (see its comment), so leave the pending key undefined — do not call `noteEdit`.

**Replace on purpose.** `applyPreset` and `applyModel` already replace the whole board; the write effect
then writes the new board. Also clear the copy synchronously inside both (`clearOpenBoardCopy()`), so
nothing stale can be read back if the page dies inside the debounce window. A rack delete
(`setModelId(null)`) keeps the board and drops the id — the write effect records that on its own.

**Comments to update.** The store's header ("An anonymous or never-saved board still lives here only, and
is gone on reload exactly as it always was") and `DesignState.boardName`'s comment ("an unsaved board is
gone on reload exactly as before") are now false — rewrite them to say the open board is kept in the
browser and comes back on the next load, with the rule from this task. Add a short paragraph to the header
naming the helper module, the key, what is kept (snapshot + modelId + owner + locked + dirty), what is not
(undo history, saveStatus), and the owner rule.

though, a `page.reload()` or a second `page.goto()` after an edit now brings the edited board back where
it used to start the stock board. Eighteen `page.reload()` calls exist; read each one's intent:

Second `page.goto()` calls after an edit inside one test are the other place this can bite (for example a
test that edits, then `goto("/")` and clicks a preset — the home page now shows the replace-board
confirmation for a board in progress, and the rack shows an "in progress" card). The executor must run the
FULL suite and judge each failure by the test's intent: where it wanted a fresh board, clear the key (or
open a new page) before the load; where it proves a preference survives, leave it alone. The GSD plan
should say this explicitly so the executor does not "fix" a test by weakening its assertion.

**One new spec**, e.g. `e2e/open-board-reload.spec.ts`, proving the fix on the `desktop` project and one
phone project (`iphone` or `android` — see `playwright.config.ts`; most specs run on all three):

1. Start the Fish from the home page (copy `openPreset` from `e2e/wings.spec.ts` line 903: `goto("/")`,
   the button with "Start Shaping" and "Fish", then wait for `/design/outline`), walk to ROCKER by a
   client-side link (the top bar's ROCKER link on a computer; on a phone the ☰ sheet's ROCKER tile —
   `e2e/helpers/screens.ts` has the screen list; or simply `page.goto("/design/rocker")` AFTER the fix,
   since a hard load is exactly what is being proved — but prove the client-side walk too if cheap), wait
   for the BLANK button (`waitForBlankButton` in `e2e/helpers/blank-picker.ts`) and read the picked card
   (`pickedCard(page)`) text — the blank's name — plus one or two figures (e.g. the DATASHEET's centre
   thickness or the dims line). Also type a board name if cheap (the Summary's Board Name box or the band).
2. `page.reload()`, wait for the BLANK button again, and expect the SAME blank name and figures (and name).
3. A fresh browser context (`browser.newContext()` or a second `test`) still gets the stock board: ROCKER
   shows "Pick a Blank".
4. A corrupt copy is ignored: `page.addInitScript` writes garbage under the key → the page loads with no
   `pageerror` and the stock board.
5. Optional: the stored copy parses (`page.evaluate` → `localStorage.getItem(key)`, `JSON.parse`, the
   snapshot's `design.blank.copy.name` equals the picked name).

Dismiss the sign-in banner and the toolbar tip the way the other specs do (`BANNER_DISMISSAL_KEY` from
`../lib/models/banner-dismissal`, `TOOLBAR_TIP_DISMISSAL_KEY` from `../lib/models/toolbar-tip`, written by
`addInitScript`).
