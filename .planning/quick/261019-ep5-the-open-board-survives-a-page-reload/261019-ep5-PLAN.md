<flags_where_the_code_contradicts_the_brief>
The brief's design is followed; these are the places the code forces a specific mechanism, with the reason.
- F-1 (B§2 Read) "read the copy ONCE in an effect (guarded by a ref)". The effect body cannot call setState (M1), so the read-back runs inside `queueMicrotask` queued by the effect, and the guard ref is set INSIDE the microtask, not before queueing. Reason: React's StrictMode (dev, so the whole browser suite) runs mount effects twice; a timer whose cleanup cancels it, with the ref set before scheduling, would cancel the only scheduled restore and then block the second run — dev would never restore. With the microtask, the first queued callback restores and the second sees the ref and does nothing. The microtask also runs before any click can be processed after the page wakes, and the storage read happens inside it, after any `applyPreset` that already cleared the copy.
- F-2 (B§3 outline-ghost) "clear the key before the reload (`page.evaluate` → `localStorage.removeItem`)". An in-page clear can be undone: when the last edit is under 250 ms old, the leaving page's pagehide flush writes the copy back during the reload. So a test that wants a fresh board uses `page.addInitScript` that removes the key at the start of every later load (`forgetOpenBoardOnEveryLoad` in `e2e/helpers/open-board.ts`), which runs after the old page's flush and before the app reads.
- F-3 (B§3) The count of `page.reload()` calls is 19, not 18 (M5); the table covers all of them.
- F-4 (B§2 Comments) Besides the two sentences the brief names, the header's sentence saying the autosave timer is the only effect that writes state becomes untrue (the read-back and the owner drop also write state) — rewritten in Task 2.
