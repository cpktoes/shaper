# The bench's slider fill painted over its own stroke

## The reported bug

The specimen's `.s-range` (the accent-filled portion of the slider track) was outset over
the track's 1px `--surf-ink` border on the top, bottom and left via a negative `inset`. That
painted the stroke away wherever the fill sat, leaving only the unfilled remainder and the
thumb with a visible edge. In the live app, `.slider-accent` in `app/globals.css` deliberately
seats the range *inside* the track's border (`border-width:0`, clipped by the track), so the
ink hairline wraps the whole control — filled range included. The bench was showing exactly
the ungrounded fill that treatment exists to prevent; `--surf-accent` is only 1.54:1 on white,
so it can never carry its own edge.

The live technique (a sibling thumb plus `overflow:hidden` on the track) couldn't be copied
verbatim because the bench's thumb is a *child* of `.s-track` at both call sites, and clipping
would also clip the thumb, which overhangs the 6px track. Fixed instead by seating the fill on
the track's padding box (`inset:0 auto 0 0`, landing exactly on the 4px interior under
`box-sizing:border-box`) with left-only pill rounding (`border-radius:99px 0 0 99px`), which
reproduces the same visual result without touching the markup.

## Also fixed: the specimen thumb was 13px, the app's is 12px

A second, lower-stakes fidelity slip found alongside the reported bug and named explicitly as
optional in the plan. Fixed anyway — it was a one-line change with a clean automated gate and
no reason to leave it half-done: `.s-thumb` moved from `13px`/`margin:-7px 0 0 -7px` to
`12px`/`margin:-6px 0 0 -6px`, matching the live app and correctly halving the centring margin
(the old 13px/-7px pairing wasn't even self-consistent).

## Verified

Both grep gates pass: `.s-range` shows `inset:0 auto 0 0`, `border-radius:99px 0 0 99px`, no
leftover `-1px`, `width:62%` unchanged; `.s-thumb` shows `width:12px`, `height:12px`,
`margin:-6px 0 0 -6px`, stroke and position unchanged. The `.s-track`/`.s-range`/`.s-thumb`
markup is byte-unchanged at both call sites (lines 303 and 357). `git diff --name-only` lists
only `.planning/sketches/themes/colour-bench.html` — no app source touched.

The plan's `<human-check>` blocks (visual confirmation of the hairline wrapping the fill in a
light and a dark theme, and the thumb sitting centred) are the orchestrator's to run in a
browser and are still pending. Republishing the bench artifact to its recorded URL is also the

## Pattern worth naming

This is the second bench-fidelity bug found in two days, after 260825-rmb's track-token
mismatch (the specimen tracked `--surf-ground` where the app draws from `--surf-well`). Both
bugs are the same shape: the bench is a hand-maintained mock of the app's real CSS with no
build step and no import linking them, so nothing catches drift except deliberately comparing
mock against measured reality — which is what 260825-rmb's audit did, and what surfaced this
plan's second, unreported thumb-size slip. Two bench-fidelity fixes in two days is a pattern,
not a coincidence: every future bench change should budget time to re-audit the whole specimen
against `getComputedStyle` on the live control, not just fix the one symptom that was reported.
