# Phase quick-260830-1g3 Plan 01: Toolbar buttons fill with the accent colour Summary

**Seven small toolbar buttons over the Template and Rocker drawings now fill with the accent colour on hover and stay filled while a real toggle (construction lines, wide view) is on, replacing the old muted-grey hover and the single accent-reserved button.**

## Performance

- **Duration:** ~15 min
- **Tasks:** 3 of 4 completed (Task 4 is a blocking human-verify checkpoint, deferred — see below)
- **Files modified:** 2 code files, 1 new todo file (not committed by this executor, see Handoff/Todo notes)

## Accomplishments

- All four Template buttons (Export Template, Rotate, Construction Lines, Wide view) and all three Rocker buttons (Rotate, Construction Lines, Wide view) now share one base hover rule: accent fill, accent border, on-accent icon colour.
- Construction Lines and Wide view on both screens additionally carry a three-class `aria-pressed:` add-on so the fill persists the whole time the toggle is ON — hovering an already-ON button changes nothing, because hover and pressed now paint the identical accent variant.
- Export Template's old `aria-expanded:` open-state background was removed (D-02): it was invisible behind the open dialog anyway, and sat at equal CSS specificity with the new hover fill.
- The Template's Construction Lines button's `aria-pressed:hover:bg-surf-accent` override was removed (D-03): once hover paints the same accent fill as pressed, there is nothing left for the override to defend against.
- Six stale code comments (four in `outline-editor.tsx`, two in `rocker-editor.tsx`) that argued for the old "only one button may take the accent fill" rule are rewritten to describe the new shared rule and record the D-01/D-02/D-03 reasoning.
- Icon-on-fill contrast measured for all four themes — every one clears 4.5:1 (see table below).
- A todo recording the D-04 extraction-decision trigger was written (not committed by this executor — see Handoff notes).

## Measured Contrast (all four themes)

Computed via a throwaway WCAG relative-luminance script under the scratchpad directory (not committed — `lib/design/contrast.ts` was deliberately deleted in quick task 260824-i05 and is not recreated here).

| Theme | Icon-on-fill (on-accent vs accent) | Fill vs panel (accent vs panel) | Ring vs panel (accent-ink vs panel) |
|---|---|---|---|
| Daylight | **7.21:1** | 2.01:1 | 6.77:1 |
| Chalk | **5.40:1** | 3.58:1 | 10.57:1 |
| Slate | **7.73:1** | 2.16:1 | 5.14:1 |
| Phosphor | **6.32:1** | 6.32:1 | 7.00:1 |

**Icon-on-fill (the bar the plan set — every theme must clear 4.5:1):** all four themes pass, landing in the expected ~5:1-8:1 band. No number fell outside that band, so no token was misread.

**Fill-vs-panel observation (for the founder, not a blocker):** Daylight (2.01:1) and Slate (2.16:1) are genuinely low — a switched-on button swaps its `surf-line` border for `surf-accent` and loses its outline into the panel behind it in those two themes. This is the exact treatment the Template's Construction Lines button has already been shipping (it was the one accent-filled button before this change), extended here to six more buttons. Chalk (3.58:1) and Phosphor (6.32:1) read with a clearer edge. This answers the plan's Task 4 checkpoint question about the switched-on outer edge: it is softer in Daylight/Slate by the same amount it already was for the one pre-existing accent button.

**Ring-vs-panel observation (unchanged by this task, measured to confirm):** the focus ring draws outside the button's border box onto the panel and was not touched — all four themes remain well above 3:1 (5.14:1 to 10.57:1).
