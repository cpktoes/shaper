<objective>
Make the small icon buttons that float over the drawing on the TEMPLATE and ROCKER screens
fill with the accent colour when the pointer is over them, and stay filled the whole time a
toggle is switched ON. No fill when off.

Purpose: the founder wants these buttons to announce themselves. Today hovering them turns
them a muted grey and only one of the seven — the Template's construction-lines button —
ever shows an ON state. The result is a toolbar where you cannot tell at a glance whether
construction lines or wide view are switched on, and where hovering gives almost no feedback.

Output: seven buttons across two files sharing one fill rule, six stale code comments that
argue for the old rule rewritten to describe the new one, measured icon-on-fill contrast for
all four themes, and a todo recording the extraction decision with its trigger.
</objective>

<decisions>

Four judgment calls, decided here so the executor does not have to reopen them.

**D-01 — Which buttons stay filled when ON: Construction lines and Wide view only (four of
the seven).** Those two are genuine on/off toggles — the overlay is either drawn or it is
not, the sidebar is either hidden or it is not — and both already carry `aria-pressed` on
the element, so the styling has a truthful hook to hang on. Rotate does not get a persistent
fill: it flips the board between horizontal and vertical, and neither orientation is
"switched on". That is not only a taste call — Rotate carries no `aria-pressed` today, and
adding one to drive a fill would announce a pressed/unpressed toggle to a screen-reader user
where none exists. Rotate gets the hover fill and nothing more.

**D-02 — Export Template gets the hover fill only, and loses its existing open-state fill.**
It opens a dialog that covers the drawing, so any fill painted on the button underneath is
invisible while the dialog is open and only flashes as it closes. Worse, keeping it would
leave `aria-expanded:bg-surf-well` and `hover:bg-surf-accent` on the same element at equal
CSS specificity, where which one wins depends on the order Tailwind happens to emit them —
a silent, order-dependent conflict for a state nobody can see. Removing it makes the two
non-toggle buttons (Export Template and Rotate) behave identically. Flagged for the founder
at the checkpoint.

**D-03 — Hover-while-ON is made safe structurally, not by an override.** Today the Template's
construction button carries `aria-pressed:hover:bg-surf-accent` purely to stop the grey hover
from overriding its accent fill. Once hover paints the *same* accent fill, that override has
nothing left to beat — the two rules set an identical value, so whichever wins the result is
the same. It is therefore removed rather than copied to six more buttons; leaving a class
whose only job is to defeat a rule that no longer exists is exactly the stale artifact this
change is cleaning up elsewhere. The comment left in its place records why.

**D-04 — Do NOT extract the shared className; mirror it, and log the trigger.** These two
files already duplicate an entire SVG icon component (`RotateBoardIcon`, defined separately
in each), and `rocker-editor.tsx`'s own header states the posture in as many words: "a
faithful local mirror, not a shared extraction". A quick task about a fill colour is not the
place to overturn a standing, explicitly-documented decision between these exact two files.
The precedent the orchestrator flagged (quick task 260830-122, which declined to extract a
shared `SliderRow`) points the same way. Instead this plan writes a todo carrying the trigger
condition — the moment a third screen grows this toolbar, extract the whole button once and
migrate all three together. That is the same shape 260830-122 used, so the repo ends up with
one consistent rule about when to extract rather than two competing ones.

</decisions>

<the_rule>

One base string for all seven buttons, plus a three-class add-on for the four that toggle.

**Base** (every button — `{N}` is each button's existing right-offset, unchanged):

`absolute top-0 right-{N} z-10 flex cursor-pointer items-center rounded-md border border-surf-line bg-surf-ground p-1 text-surf-ink-muted transition-colors outline-none hover:border-surf-accent hover:bg-surf-accent hover:text-surf-on-accent focus-visible:ring-2 focus-visible:ring-surf-accent-ink`

The only change from today's base is that the two-class neutral hover pair is replaced by the
three-class accent hover trio — background, icon colour and border move together, so a hovered
button is pixel-identical to a switched-on one. That is the point: hover previews ON.

**Toggle add-on** (Construction lines and Wide view on both screens), inserted between the
hover trio and `focus-visible:`:

`aria-pressed:border-surf-accent aria-pressed:bg-surf-accent aria-pressed:text-surf-on-accent`

Every accent fill is paired with `text-surf-on-accent` on the same variant. That pairing is
not optional decoration — `--surf-on-accent` exists precisely to be the foreground on
`--surf-accent`, and this codebase has shipped the bug of leaving an icon on the muted ink
token over an accent fill three times (see `.planning/quick/260825-rmb-*/SUMMARY.md`). Fold
the icon colour into the same variant as the fill, never onto a separate always-on class.

Both `--surf-accent` and `--surf-on-accent` are contract tokens re-pointed per theme in
`app/globals.css`, so all four themes follow automatically. Do not introduce a new colour and
do not hard-code a hex anywhere in this change.

</the_rule>
