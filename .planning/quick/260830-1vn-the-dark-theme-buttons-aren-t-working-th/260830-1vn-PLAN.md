Give the ON state its outline back. Right now, switching Construction Lines or Wide view on
takes the crisp grey edge OFF the button and replaces it with a soft accent-coloured one —
so in the dark themes an ON button reads as LESS defined than its switched-off neighbours,

that the same change also swapped the button's neutral border for an accent border, and an
accent-coloured hairline is nearly invisible against a dark page. The button goes soft
exactly at the moment it should go crisp.

## What was measured, and what we are doing about it

The mechanism is not broken in dark. In the slate theme an ON button really does paint
`#18526d` behind a `#f2f4f7` icon at **7.73:1** — the classes carry no `dark:` variants and
resolve through the `--surf-*` contract, so both modes run the identical rule. The defect is
perceptual, and it has one provable cause: **turning a button ON makes it lose its edge.**

Border-versus-page contrast, measured from the four ramps in `app/globals.css`:

| theme | ON border today (accent) | ON border after this fix (`--surf-line`) |
|---|---|---|
| daylight | 2.01 | **4.13** |
| chalk | 3.58 | **4.13** |
| slate | **2.16** | **3.70** |
| phosphor | 6.32 | **3.80** |

Three of those four numbers are below 3:1 — and `components/outline/outline-editor.tsx`'s
own rotate-button comment already states the rule they break: *"The border is `surf-line`,
not `surf-line-faint` — `line` is the token carrying the 3:1 non-text target a control
boundary needs in every theme."* The accent has no such guarantee. It is a fill token, and
the naming rule at the top of `globals.css` says so in as many words: a colour without
`-ink` is a fill and must never be used as a bare stroke. The border swap put a fill token
on a stroke, and the dark themes are simply where that shows up first.

**Decision: keep the neutral border in every state.** Delete `hover:border-surf-accent` and
`aria-pressed:border-surf-accent` from all seven toolbar buttons. The fill stays, the
on-accent icon colour stays, the toggles still hold their fill while ON. This is pure
subtraction: no new token, no palette edit, no change to the three-layer cascade. It fixes
all four themes at once (daylight's 2.01 was quietly just as wrong, it simply reads as an
obvious hue shift at the light end and got away with it), and it restores the repo's own
precedent from quick task 260823-qr3, which put a neutral hairline on accent-filled controls
for this exact reason: *"everything else this app draws is defined by a stroke, and an accent
fill with no edge was the one place that language dropped."*

**We are deliberately NOT boosting the dark fill in this task.** With the crisp edge back,
the ON state in a dark theme carries three simultaneous signals: a `#6a707c` edge at 3.70:1,
a fill that lifts off the page, and an icon that jumps from muted `#a1a8b4` to near-white
`#f2f4f7`. That is very likely enough, and shipping the smaller change first is how we find
out for certain rather than guessing. The checkpoint asks the founder that exact question.

**If the founder says the dark fill is still too dim**, the follow-up is already scoped and
is NOT a swap to `--surf-accent-ink` — that token is a *dark* colour in the light themes
(daylight `#48605c`), so using it everywhere would repaint the light appearance the founder
approved an hour ago. The follow-up is a new contract token `--surf-control-fill`, assigned
in all six contract blocks: in the two light blocks it is assigned `var(--ramp-daylight-accent)`
/ `var(--ramp-chalk-accent)`, i.e. the exact same value those buttons resolve today, so the
light themes are provably byte-identical (same computed hex, verifiable by reading the
button's `backgroundColor` before and after); only the two dark blocks get a brighter value.
That is a separate quick task. Do not start it here.
</decision>
