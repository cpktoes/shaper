<objective>
Make one screen work on a phone, end to end, and build the shared shell every other screen will move
into.

A shaper opens TEMPLATE on a phone. The board drawing sits pinned across the top, filling the width;
the controls scroll underneath it, so a slider can be moved while the board stays in view. The board
stands nose-up when the phone is upright and lies flat when the phone is turned. The drag points are
already showing, because on a phone the drawing is the control. Along the bottom, under the thumb,
six labels move between the screens. Across the top, the wordmark, the Save state and one menu
button holding Units, Theme and the account. Nothing is hidden — the eight sliders that just repeat
what a drag point already does are folded into one "Fine adjust" group at the bottom of the list,
one tap away.

On a desktop nothing at all has changed, and the five baseline pictures from 09-01 prove it.

Purpose: this is the phase's tracer. Every layer the phase will touch — the CSS tokens, the root
viewport, the shared shell, one screen, the phone chrome, and the automated proof — is wired
together on one path before any of it is repeated. If the architecture is wrong, it is wrong after
one commit instead of after ten.
Output: two CSS tokens, a dvh root with a viewport export, the shared shell, the phone bars, the
TEMPLATE phone layout, and a Playwright spec that proves it on an iPhone and an Android.
</objective>

<assumption_delta_decision surface="layout">
**The noun that is now primary: the shared shell, not the five editors' own copies of it.**

Until this plan the app had exactly one layout class — desktop — expressed five times, once per
editor, with zero breakpoints. From here it has two, expressed once.

**Decision: promote-with-variant.** `components/design/design-screen-shell.tsx` becomes the single
owner of the sidebar-beside-canvas layout, and the desktop rendering is its *unprefixed base*, kept
byte-identical. The phone is a `max-shell:` variant layered on that base, never a second branch and
never a default flip. Not `add-alongside`: a second phone-specific shell rendered beside the desktop
one would be the "fix the layout five times" risk the roadmap names, one layer up.

Rationale: one shell means the phone layout is written once and the desktop layout cannot drift; the
additive-variant form is what makes PHON-05 provable by construction rather than by inspection — a
desktop mouse at desktop width never enters a `max-shell:` rule at all, so the 09-01 baselines are
the whole proof.
</assumption_delta_decision>
