<objective>
Stop a phone from offering a Print button that cannot print.

A shaper tapped Print on their iPhone and nothing happened. The debug session proved the app does
its job perfectly: the tap lands on the button, and the browser's print is called straight away,
inside the tap, on the dev build and on the deployed site alike. What fails is downstream, in iOS
itself — the site had been opened from its Home-Screen icon, and iOS 26 now opens every
Home-Screen site as its own little app rather than as a Safari tab. Printing from inside one of
those is a documented dead end: the call goes out and nothing comes back. Typing the address into
Safari and tapping Print works.

So the founder's decision: on a phone, when the site is running as a Home-Screen app, put a plain
note where the Print button was — printing isn't available here, open this page in Safari to print
the full-sized rail — and leave printing itself completely alone. No PDF path, no share sheet, no
change to a single line of the print stylesheet. A button that quietly fails is replaced by a
sentence that tells a shaper what to do.

The detection is a media query, not JavaScript — the browser already knows how it was launched and
will tell CSS, which is the same rule the rest of the phone work follows. And it is gated on the
phone width too, because a desktop installed web app prints fine.

Purpose: closes G-09-6 from the phase's own UAT (PHON-01 and D-13 — the phone View Full Sized
dialog).
Output: the note, the CSS-only swap, and the three assertions that were missing — that tapping
Print really calls print, that the Home-Screen case shows the note, and that the desktop is
untouched.
</objective>

<assumption_delta_decision surface="how the app knows it was launched from the Home Screen">
**The condition is written inline in this one file as a Tailwind arbitrary variant, not as a named
variant in the app stylesheet.**

Two spellings reach the same CSS. A named variant declared once in `app/globals.css` beside the
existing pointer variant, used as `max-shell:standalone:hidden`; or Tailwind's arbitrary-variant
syntax written at each call site, `max-shell:[@media(display-mode:standalone)]:hidden`. Both were
compiled against this repo's own Tailwind 4 install before this plan was written; both produce
`@media (width < 820px) { @media (display-mode:standalone) { … } }`, which is exactly the intended
pair of conditions.

**Decision: the arbitrary variant, inline.** Two reasons, in order of weight.

First, the practical one: the gap-closure plan running in the same wave as this one owns
`app/globals.css` outright, and two plans editing one stylesheet in parallel worktrees is a merge
conflict waiting to happen. Writing the condition here keeps this plan's three files disjoint from
that plan's ten, which is what lets both run at once.

Second, the durable one: a named variant in the stylesheet advertises an app-wide switch. This is
not one. It exists in exactly one dialog, on one screen, for one iOS quirk, and there is no second
place in the app that should quietly start behaving differently because the site was opened from an
icon. `--breakpoint-shell` and the pointer variant earned their names by governing every screen;
this does not, and a named variant would invite exactly the sprawl the phase has been careful to
avoid. Four call sites in one file, each carrying the condition in full, is the honest shape.

If it ever spreads beyond this dialog, promote it to a named variant then — with a comment beside
the other two switches explaining that launch context is a third independent axis, never conflated
with width or pointer.
</assumption_delta_decision>
