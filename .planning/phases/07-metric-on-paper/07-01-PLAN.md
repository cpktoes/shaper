<objective>
Make the chosen units system reach the printer, and make the Full Sized Template read in it.

This is the first leg of Phase 7 and it carries the phase's one architectural question: can the
printed labels change system without the drawn board moving? The answer has to be proved, not
assumed, which is why this plan leads with a single thin path — the gear-menu chooser, through the
export dialog, into the PDF builder, down into the pure geometry file that composes the label text,
and back out onto a printed station mark — before anything else expands from it.

Purpose: a shaper who works in millimetres gets a Full Sized Template whose marks, scale-check
caption and name block read in millimetres and centimetres, while the template itself still measures
dead true against a ruler and a shaper working in inches sees a page identical to yesterday's.

Output: the units channel wired end to end into all three PDF builders; the Full Sized Template's
station labels, scale-check caption, how-to box and name/dims block reading in the chosen system;
one net-new pure formatter for the calibration square's tenth-of-a-millimetre figure; the three
frozen characterisation pins still green and untouched.
</objective>

<discretion_decisions>
Two questions `07-CONTEXT.md` left to the planner are settled here. Do not re-open them; the other
plans in this phase assume these answers.

**1. Printed label text stays inside `lib/geometry/template.ts`, with `UnitsSystem` threaded through
and defaulted to imperial.** The alternative — moving label composition out to the three PDF
builders — is architecturally attractive (it would restore the geometry file's display-agnostic
posture) but it is *forbidden by the frozen pins*, not merely more work. All three pins hash
`JSON.stringify` of objects that include `placements`, `lineSegments`, `segments` and `rows`, and
each of those carries a `label` / `text` string field. Removing the `label` key to move composition
out changes the shape of the hashed object, which changes all twenty-four digests, which would
require regenerating the pins — the one thing this phase must never do. Threading a
`system: UnitsSystem = "imperial"` parameter instead leaves every existing zero-argument call site,
including the pins' own, producing a byte-identical string by construction. That is why the pins
stay green without a metric branch.

**2. The conversion ledger grows inside `lib/units-isolation.test.ts` rather than in a new file.**
This lands in Plan 05 and is recorded here so no plan starts a second mechanism.
</discretion_decisions>

<assumption_delta_decision>
**Noun now primary:** *a printed measurement* — previously "an inch measurement drawn on a page",
now "a measurement drawn on a page in the shaper's chosen system".

**Decision: `add-alongside`, deliberately and asymmetrically.**

At the PDF-builder boundary the printed system is genuinely **promoted** to a first-class
parameter: `system: UnitsSystem` is a *required* field on all three `Build*PdfOptions` with no
default, so a caller physically cannot build a PDF without stating which system it is for.

Inside `lib/geometry/template.ts` it is **added alongside**: every label-composing function takes
`system: UnitsSystem = "imperial"`, which keeps imperial as the hardcoded primary in that one file.
This is accepted debt, and it is not a matter of taste — the frozen characterisation pins call these
functions with no argument, and that is exactly what makes them able to prove nothing on paper moved.
Removing the defaults would either break the pins or require regenerating them.

**What would force a later promote:** the day the frozen pins are legitimately superseded — a future
phase that genuinely changes the template's drawn geometry and re-pins it against a new baseline —
the `= "imperial"` defaults in `lib/geometry/template.ts` should be deleted in the same change and
`system` made required there too. Until then the defaults are load-bearing, not laziness.
</assumption_delta_decision>
