<objective>
Ship it: the deployed site gets its own Clerk production instance, its own Google credentials
and its own migrated database, and then a shaper walks the whole phase end to end on the live
site before it is called done.

Purpose: every remaining way this phase can fail is invisible locally. Clerk's development
instance uses shared Google credentials that production does not get. The deployed site talks to
a different Neon branch than the laptop does. And the Vercel project currently holds no
environment variables at all — Phase 1 deployed with zero secrets by design, which stops being
true here.

Output: a live site where a real shaper can make an account and keep their boards, verified by
walking it rather than by inferring it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dashboards -> deployment | Production keys move by hand from Clerk, Google and Neon into Vercel; every hop is a chance for a secret to land in the wrong place |
| repo -> the world | The repository is public-shaped and permanent; a secret committed here cannot be un-committed, only rotated |
| internet -> live site | This is the first deployment of this app that holds a shaper's data behind an account |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-08 | Information Disclosure | Production secrets | high | mitigate | Secrets live only in the Vercel environment and the shaper's own dashboards; `.env.example` carries names with no values, `.gitignore` already covers `.env.*`, and Task 2's acceptance criteria grep this phase's commits for live key and connection-string shapes |
| T-02-17 | Spoofing | Development Clerk keys used in production | high | mitigate | The production instance issues its own pk_live_/sk_live_ keys and rejects the development ones; Task 1 names them by prefix so a mismatch is visible rather than subtle |
| T-02-18 | Spoofing | Google OAuth redirect URI mismatch | medium | mitigate | The Google client's authorized redirect URI is taken from Clerk's production instance rather than guessed; the walkthrough exercises Google sign-in on the live site specifically because this failure appears only there |
| T-02-03 | Elevation of Privilege | Cross-account access on the live site | critical | mitigate | Enforced in code by the ownership scoping in `app/design/actions.ts` and `lib/db/queries.ts`, guarded by `lib/db/ownership.test.ts`, and exercised on the live site by signing in as a second account during the walkthrough if one is available |
| T-02-19 | Denial of Service | Deployed site pointing at an unmigrated database | high | mitigate | Task 2 applies the migration to the production branch and then proves it by saving a real board through the deployed site, rather than trusting a green build |
</threat_model>
