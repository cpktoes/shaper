<objective>
Give the units preference its account home, so a shaper's choice follows them to any device they
sign in from, and wire the sign-in handoff that decides which of the two stored values wins.

Purpose: UNIT-03 and the account half of UNIT-04. 05-01 proved the chain end to end for one
browser; this plan adds the second storage home without changing the shape of anything it built —
`resolveUnitsHandoff` gains real `signedIn` and `account` inputs, and the provider gains the
background write it was left a slot for.

Output: a `user_preferences` table with a nullable units column, a migration applied to the Neon
development branch, an auth-first Server Action to write it, and the reconciliation rule wired end
to end.

    migration run against production, in the deploy-then-migrate order CLAUDE.md mandates.

    the same reason `lib/models/autosave.ts` keeps `decideAutosave` out of the component: a policy
    inlined in a component silently drifts. Export `UNITS_WRITE_RETRY_DELAYS_MS: readonly number[]`

    discrete click, not a stream of slider drags, so there is no debounce, only a bounded retry
    ladder) and `nextUnitsWriteRetryDelayMs(attempt: number): number | null` returning `null` once
    the ladder is exhausted. Document why it is bounded: between the push to `main` and the
    production migration the table does not exist yet, and an unbounded retry would hammer the
    database for every shaper who touches the chooser during that window.

    page, exactly the way `BoardRackData` degrades a failed board-list read to an empty rack. Then
    return `decideUnitsHandoff({ signedIn: userId !== null, account, browser })`. The function's
    signature and return type do not change; only its inputs become real.

    **`components/units-provider.tsx`** — three additions:
    1. **The promotion effect.** When `handoff.promoteToAccount` is non-null, call
       `saveUnitsPreference` with it once on mount (guarded by a ref so a re-render cannot fire it
       twice). This is the browser's explicit choice being adopted by an account that had none
       (UNIT-04). It is fire-and-forget through the same write helper as a click.
    2. **The adoption effect** (the branch 05-01 created): when `handoff.adoptIntoBrowser` is
       non-null and differs from what is stored, write it to `localStorage` and the cookie and emit
       — the account's choice reaching the browser, so the two never disagree (D-09).
    3. **The background write on a pick.** `setSystem(next)` keeps writing both browser stores
       synchronously and emitting first, so the screen switches on the click; only then does it
       start the account write. Implement the write as a small internal helper holding an attempt
       counter and a `setTimeout` handle in refs: call `saveUnitsPreference(system)`; on rejection,

       rejected write may never be reported as success or cause the on-screen system to change
       (the `nextStatusAfter` discipline from `lib/models/autosave.ts`), and a **newer pick cancels
       any pending retry and resets the attempt counter**, so a stale retry can never write an
       older system over a newer one. Clear the pending timeout on unmount.

    Nothing here changes what the shaper sees when a write fails: there is no toast, no banner, no
    spinner and no reverted check (D-11, and the UI-SPEC's error row says so explicitly).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Server Action | `saveUnitsPreference` is callable by anyone with a session; its argument arrives over the wire and is untrusted. |
| Server Action → Postgres | The write reaches a per-shaper row; the owning identity must come from the session, never the payload. |
| Postgres → server render | The stored `units` value is read back and used to choose a formatter; it may hold anything a past bug or hand-edit left there. |
