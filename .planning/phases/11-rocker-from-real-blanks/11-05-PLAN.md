<objective>
Put the three vendor catalogues into the database, and give the ROCKER screen a safe way to read them.

This plan adds a `blanks` table — one row per blank, its station rows kept exactly as the catalogue
printed them — writes the migration, applies it to the development database, and seeds all 162 blanks
from the committed CSVs through the tested reader from 11-01. The seed is safe to run again: blanks
update by vendor and name rather than duplicating.

It also adds the one read the ROCKER page will make: the pickable blanks (158 — the four Marko SUP
blanks with no usable thickness stay stored but out of the list). That read never breaks the page: if
the table is not there yet (production between the code going live and the founder running the
migration), is empty, or the database is unreachable, the screen shows "The blank catalog didn't load"
and a board that already has a blank keeps working from its own copy.

Browser tests run without a database, so the test server reads the same catalogue from the CSVs.

Purpose: R7, R8, R9; D-20. The production migration and seed are the founder's, after the deploy
(plan 11-13).
Output: the table, migration 0004, `lib/db/blanks.ts`, `scripts/seed-blanks.ts`, the development
branch migrated and seeded, the Playwright source switch.
</objective>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-11-11 | Elevation of Privilege | `lib/db/blanks.ts` | high | mitigate | Read-only by construction: ownership test asserts only `db.select` from `blanks`, no insert/update/delete, no owner parameter; blanks has no user column |
