<task type="checkpoint:human-action" gate="blocking">
  <name>Task 2: Push, let Vercel deploy, then migrate production — in that order</name>

  <action>
    Everything in Phase 5 is built: the Units chooser in the gear menu, the shared preference with
    its browser and account homes, the metric number rules in `lib/geometry/units.ts`, the preset
    and rack cards reading in the chosen system, and the two folded refactors. The only thing left
    is getting it onto the live site and adding the new table to the production database — in that
    order.

    This step is deliberately not automated. It touches the Neon **production** branch, where a real
    shaper's saved boards live, and CLAUDE.md's database rule is absolute: push the code, let Vercel
    finish deploying it, and only then migrate. No agent runs `npm run db:migrate:prod`.
  </action>

  <instructions>
    Do these in order and do not skip ahead.

    1. **Push the code.**
       `git push origin main`

    2. **Wait for Vercel to finish deploying.** Watch the deployment at https://vercel.com (or run
       `npx vercel ls`) until the production deployment for that commit reports Ready. Then load
       https://shaper-coral.vercel.app and confirm the site works: the gear menu shows the Units
       group, and picking Metric re-labels the cards.

       At this point the new table does not exist yet, and that is expected and safe. Your choice
       will be remembered by that browser but will not follow you to another device. Nothing should
       look broken and no error should appear.

    3. **Only now, migrate production.**
       `npm run db:migrate:prod`

       This pulls a transient production environment file, applies the migration, and deletes that
       file when it finishes. It should report one migration applied. Run it a second time — it
       should report nothing left to apply.

    Never run step 3 before step 2 has finished. The deployed site has to already understand the new
    table before that table exists, or the live site ends up reading a database it was not built for.

    If anything fails, stop and say what happened rather than retrying — a half-applied migration on
    production is worth a conversation.
  </instructions>

  <verification>
    - `git log --oneline origin/main -1` shows this phase's final commit on the remote.
    - The Vercel production deployment for that commit reports Ready, and
      https://shaper-coral.vercel.app loads with the Units group present in the gear menu.
    - The first `npm run db:migrate:prod` reports one migration applied; a second run reports
      nothing left to apply.
    - No file matching `.env*` was created or left behind — the pulled production env file is
      deleted by the script's own exit trap.
  </verification>

  <resume-signal>Type "deployed and migrated", or describe what went wrong and at which step</resume-signal>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local machine → production database | `npm run db:migrate:prod` pulls a transient production environment file and runs a schema change against the branch holding a real shaper's boards. |
| main branch → live site | A push to `main` deploys to production automatically. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-26 | Denial of service | migrating production ahead of the deploy | high | mitigate | The order is enforced by making this a blocking human-action checkpoint with the three steps written out and the reason stated. No agent runs the production migration, and the deployed code degrades safely while the table is absent, so even a delayed step-3 leaves a working site. |
| T-05-27 | Tampering | a migration that alters the boards table | high | mitigate | Task 1 reads the generated SQL and asserts it only creates the new table; the migration was generated by drizzle-kit from an additive schema change, never hand-written. |
| T-05-28 | Information disclosure | the transient pulled production environment file | medium | mitigate | Unchanged from the existing `db:migrate:prod` script, which traps EXIT/INT/TERM and deletes the pulled file. No plan step edits or copies it, and no file matching `.env*` is written by this phase. |
| T-05-29 | Tampering | a local experiment reaching production data | high | mitigate | `.env.local` points at the Neon development branch and is pulled with the Vercel CLI, never hand-edited; every earlier plan in this phase runs against development only. |
| T-05-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package. `npx vercel` is invoked by the existing `db:migrate:prod` script, unchanged from the shipping `package.json`. |
</threat_model>
