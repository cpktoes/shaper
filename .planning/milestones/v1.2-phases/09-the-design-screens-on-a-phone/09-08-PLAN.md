<objective>
Make the keyboard show where it is.

Right now a shaper who puts the mouse down and reaches for the keyboard is working blind. Tab
through a design screen's sidebar and the sliders give back nothing at all — no ring, no
highlight, no hint which one the arrow keys are about to move — and the tail-shape tiles give back
a grey-green whisper you have to hunt for. Everything *works*; you just cannot see what you are
about to change, which on a screen full of numbers a shaper is going to cut foam to is the whole
problem.

Two separate causes, both found and confirmed in the debug session, neither of them anything
Phase 9 broke — the app has been like this since the outline editor was first built. The sliders
draw their focus ring on the wrong element: the ring is written on the thumb, but the browser
actually puts keyboard focus on a tiny hidden control *inside* the thumb, so the ring's rule never
matches and nothing paints. The hand-rolled buttons have no focus look of their own at all, so all
they get is the browser's automatic outline, painted in a colour the app dims to half strength —
about 2.2:1 against a white sidebar, under the 3:1 the app's own palette contract requires of any
UI edge.

So: point the slider's ring at the element that really has focus, give every hand-rolled button one
shared ring of its own, and raise that ring to the palette's accent ink at full strength — which
measures between 5.1:1 and 10.6:1 across all four themes. Nothing at rest moves. Nothing under the
mouse moves. The five photographs of the desktop screens taken before this phase began still match,
pixel for pixel, and that is how we know.

Purpose: closes G-09-4 from the phase's own UAT (PHON-05 — keyboard operation on every viewer's
controls).
Output: one focus rule for every slider, one shared focus class for every hand-rolled button, one
strength of ring across the whole sidebar, and a keyboard test that proves it.
</objective>

<assumption_delta_decision surface="where the focus look is written">
**Two choices were open, and both are recorded here so the next reader does not have to re-derive
them.**

**1. The slider thumb: a rule in `app/globals.css`, not a Tailwind class in the primitive.**

The measured fact is that Base UI 1.7.0 renders `SliderPrimitive.Thumb` as a DIV wrapping a
visually-hidden `<input type="range">`, and it is the input that takes keyboard focus. So the
selector has to be "the thumb that *contains* something focus-visible" — `:has(:focus-visible)` —
not "the thumb that *is* focus-visible". Either spelling works: Tailwind's `has-[:focus-visible]:`
variant inside `components/ui/slider.tsx` (verified to compile), or a plain CSS rule in
`app/globals.css`.

**Decision: the CSS rule in `app/globals.css`, beside the existing `.slider-accent` hooks.** This
codebase has already written down why, twice — `components/settings-menu.tsx` ("Built directly on
Base UI's Menu primitives rather than as a `components/ui/*` wrapper, for the same reason
`.slider-accent` lives in app/globals.css: `components/ui/*` is shadcn-generated and may be
regenerated, so app-owned styling has to survive that") and `components/viewer/tabbed-panel.tsx`
(the `.slider-accent` note, "written after fourteen copies of a slider style"). The app's own
slider look already lives in three `.slider-accent` rules there; the focus ring is a fourth, in the
place the next reader will look. It also reaches every slider on every screen, because every
`<Slider>` in this app carries `className="slider-accent"` — nine direct call sites plus
`components/design/slider-row.tsx`, checked file by file.

**2. The hand-rolled buttons: one shared class, not five copies of a class string.**

There are thirteen hand-rolled `<button>`s across four files. A shared exported TypeScript class
string and a shared CSS class both avoid the copies; the CSS class wins because it puts the whole
focus treatment — thumb and buttons — in one place in `app/globals.css`, and because each button
then gains one short word rather than a fifty-character Tailwind run appended to a class string
that is already long enough to hide things in (which is precisely how the ad-hoc 30% border mix in
`outline-controls.tsx` survived two cleanup passes).
</assumption_delta_decision>
